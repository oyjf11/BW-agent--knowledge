# 冲突检测与处理规则

## 核心原则

**知识库已有事实为权威源。** 源文档是外部参考资料，可能与实际实现有偏差。冲突时以 vault 已有记录为准。

## 冲突分类

| 类型 | 判定标准 | 示例 | 处理方式 |
|------|---------|------|---------|
| 无冲突 | 源文档知识在 vault 中完全不存在，或内容一致 | 源文档描述 checkpoint 设计，vault 对应文件为空 | 直接写入 |
| 追加（非冲突） | 源文档提供了更细颗粒度的描述，但与 vault 不矛盾 | vault 用通用术语描述流程，源文档显式命名了每个 Agent 角色 | 补充写入，不覆盖已有内容 |
| 命名差异 | 同一概念使用不同名称，含义一致 | vault 写 `app_pages`，源文档写 `pages` | 统一使用 vault 的命名，写入时可注明等价关系 |
| 实质性冲突 | 核心架构判断或事实断言矛盾，无法调和 | vault 说平台数据库是 MySQL，源文档说是 PostgreSQL | 标记为「待确认」，告知用户，不写入冲突内容 |

## 处理流程

```
发现差异
  ↓
是否为核心架构矛盾或事实矛盾？
  ├─ 否 → 是否为命名差异？
  │        ├─ 是 → 统一为 vault 命名 → 写入时注明等价关系
  │        └─ 否 → 判定为追加 → 补充写入 vault（不覆盖）→ 完成
  └─ 是 → 标记「待确认」
           ↓
        通知用户：
        "发现 1 处实质性冲突：源文档称 [A]，但 vault 已有记录称 [B]。
         [A] 是否应被确认为新信息并更新 vault？还是源文档描述有误？
         请确认后我再处理。"
           ↓
        不写入待确认内容，等待用户指示
```

## 通知用户的话术模板

```
> 发现 X 处实质性冲突：
> 1. 源文档称 [具体主张 A]，但 vault 文件 [文件路径] 中记录为 [B]。
> 2. 源文档称 [具体主张 C]，但 vault 无对应实现证据。
>
> 请逐一确认：接受源文档说法（更新 vault）还是以 vault 为准（跳过）？
```

## 常见误判场景

以下场景**不是**冲突，不要误判：

| 场景 | 误判风险 | 正确处理 |
|------|---------|---------|
| 源文档比 vault 更详细 | 容易误判为"矛盾" | 这是追加。vault 写"多层架构"，源文档列了 9 层——应补充写入 |
| 源文档有额外 Agent 角色 | 容易误判为"架构不同" | vault 只列了核心 Agent，源文档补充了辅助 Agent —— 应追加角色表 |
| 源文档用英文术语 | 容易误判为"命名差异" | 如果 vault 统一用中文，写入时用中文。但若保留英文为通用惯例也可接受 |
| 源文档列出更多数据库表 | 容易误判为"过度设计" | vault 只列了部分表名，源文档补充了完整的表设计——应补充写入 |
| 源文档中的 DAG/英文缩写 | 容易误判为"需要修正" | vault 使用统一术语（如"任务依赖图"），写入 vault 时替换为中文统一术语 |

## 冲突报告格式

阶段三完成后输出：

```
## 冲突报告

| 编号 | 知识点 | 冲突类型 | vault 已有记录 | 源文档主张 | 处理结果 |
|------|--------|---------|--------------|-----------|---------|
| C-1 | xxx | 命名差异 | `app_pages` | `pages` | 统一为 `app_pages` |
| C-2 | xxx | 实质性冲突 | MySQL 控制面 | PG 控制面 | 待用户确认 |

处理摘要：
- 无冲突：N 个 → 直接写入
- 追加：N 个 → 补充写入
- 命名差异：N 个 → 已统一
- 实质性冲突：N 个 → 待用户确认
```
