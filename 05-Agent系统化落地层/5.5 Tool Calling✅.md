# 5.5 Tool Calling

> 所属分支：[[05-Agent系统化落地层/_index|05-Agent系统化落地层]]

## 子节点 / 待填充要点
- Tool Registry：工具注册、发现、生命周期管理
- Tool Schema：name、description、input_schema、output_schema、permission_scope、risk_level
- Tool Executor：参数校验、权限校验、超时控制、重试控制、结果校验、事件记录、审计落库
- MCP：工具协议标准化、外部系统封装、工具发现与调用、权限控制
- Idempotency：action_id、idempotency_key、执行前查重、执行后记录、重试安全
- Tool Security：风险分级、只读优先、写操作审批、参数校验、执行沙箱
- Result Validation：输出结构校验、业务规则校验、异常包装

## 一句话定义

Tool Calling 不是简单让 Agent 调用 API，而是将所有外部能力包装成**统一工具协议**（Tool Contract），通过 Tool Registry 注册管理、Tool Router 智能选择、Tool Runtime 安全执行，形成 Agent 与生产系统之间的标准化能力层。

## 解决什么问题

1. **接口碎片化**：MySQL、K8s、ALB、OSS 等系统 SDK/API 格式不一致，Agent 难以统一调用
2. **安全不可控**：模型直接调用生产系统可能执行危险操作（删除、重启、改配置）
3. **调用不可观测**：谁调用了什么、结果如何、有没有越权，无法追踪
4. **能力不可扩展**：新增 Redis/MQ/ES 等数据源需要改主流程

## 如何实现

### 一、Tool Contract：统一工具协议

标准工具要统一 7 个维度：

```text
ToolDefinition = {
  name           // 工具名，如 k8s.get_pod_status
  domain         // 所属领域：mysql / k8s / alb / oss
  description    // 给 Agent 理解这个工具什么时候用
  inputSchema    // 入参 JSON Schema
  outputSchema   // 出参 JSON Schema
  permission     // 只读 / 需审批 / 高危
  riskLevel      // low / medium / high
  timeoutMs      // 超时时间
  retryPolicy    // 重试策略
  audit          // 是否审计记录
}
```

Agent 看到的不是"我能连 MySQL、K8s、ALB、OSS"，而是"我有一组可调用的、受控的、结构化工具"。

### 二、工具三级分类

| 类型 | 定义 | 示例 | 安全约束 |
|------|------|------|---------|
| 查询型 | 只拿原始信息，不改变状态 | `mysql.get_slow_queries`、`k8s.get_pod_status`、`alb.get_backend_health` | 自动执行 |
| 诊断型 | 在工具内部做规则判断，返回结构化结论 | `k8s.analyze_crash_loop`、`mysql.analyze_lock_wait`、`alb.analyze_5xx_spike` | 自动执行 |
| 动作型 | 会改变生产状态 | `k8s.restart_workload`、`k8s.rollback_deployment`、`mysql.kill_session` | 必须审批 |

运维智能体第一阶段应只做查询型 + 诊断型，动作型先做模拟执行。

### 三、安全等级分级

```text
Level 1：只读查询 → 自动执行（查询日志、状态、指标）
Level 2：低风险动作 → 需要二次确认（清理临时缓存、触发健康检查）
Level 3：高风险动作 → 必须人工审批（重启服务、回滚发布、修改 ALB 后端、kill MySQL 连接）
Level 4：禁止动作 → 不允许 Agent 执行（删除数据库、删除 Bucket、批量删除对象、执行任意 shell）
```

### 四、Tool Router：工具智能选择

排查计划生成后，由 Tool Router 负责将计划步骤匹配到具体工具，判断依据包括 6 个维度：

```text
1. 排查目标层：入口层→ALB工具 / 运行层→K8s工具 / 数据层→MySQL工具 / 存储层→OSS工具
2. 证据需求：5xx指标→alb.get_traffic_metrics / Pod重启→k8s.get_pod_status / 慢查询→mysql.get_slow_queries
3. CMDB 资源补全：order-service → cluster/namespace/workload/ALB实例/数据库
4. 参数完整度：缺少 podName 时先调 k8s.get_pod_status 再调 k8s.get_pod_logs
5. 权限和风险等级：只读工具自动执行，高风险动作必须审批
6. 当前证据状态：第一轮发现 MySQL 异常→收敛到 MySQL 方向继续排查
```

工具选择评分公式：

```text
score = capabilityMatch × 0.35 + resourceMatch × 0.25 + inputCompleteness × 0.20 + safetyScore × 0.10 + freshnessScore × 0.10
```

### 五、Tool Runtime：安全执行网关

Tool Runtime 是 Agent 和生产系统之间的**安全执行网关**，Agent 不直接调用 K8s/MySQL/ALB/OSS，所有工具调用必须经过 Tool Runtime。

**架构位置：**

```text
Planner → Tool Router → Tool Runtime（统一执行控制）→ Tool Adapter → 返回 EvidenceRecord
```

**核心能力：**

| 能力 | 具体内容 |
|------|---------|
| 权限校验 | 四维度校验：用户权限 × 工具权限 × 资源权限 × 环境权限 |
| 参数校验 | JSON Schema 校验 + 安全参数校验（MySQL 禁止 UPDATE/DELETE、K8s 禁止 exec、OSS 禁止读大文件） |
| 参数补全 | 缺失参数通过 CMDB 自动补全（如 order-service → cluster/namespace/workload） |
| 超时重试 | 按工具配置 timeout + 指数退避重试 + 区分可重试/不可重试错误 |
| 熔断降级 | 工具连续失败后熔断，降级到替代工具（日志不可用→查事件、慢查询不可用→查连接数） |
| 审批强制拦截 | requires_approval=true 的工具必须审批通过才执行，防止绕过风险门禁 |
| 结果脱敏 | 敏感字段脱敏（Token/Cookie/手机号/AccessKey），只存结果摘要 |
| 证据标准化 | 所有工具返回统一转成 EvidenceRecord |
| 审计留痕 | 记录谁调用、为什么调用、调用结果、耗时、重试、权限决策 |

**完整执行流程（15 步）：**

```text
1. 接收工具调用请求
2. 读取工具注册信息
3. 校验工具是否存在
4. 校验用户/Agent/服务/环境权限
5. 判断是否需要人工审批
6. 校验参数 Schema
7. 通过 CMDB 补全资源参数
8. 做安全策略检查
9. 写入调用开始审计
10. 执行具体 Tool Adapter
11. 处理超时、重试、熔断
12. 对返回结果脱敏
13. 标准化成 EvidenceRecord
14. 写入调用完成审计
15. 返回给 Agent
```

### 六、MySQL 工具安全设计示例

```text
只允许 SELECT
禁止 UPDATE / DELETE / INSERT / DROP / ALTER
强制 LIMIT（maxRows=100）
限制查询时间窗口
限制库表白名单
敏感字段脱敏
优先使用模板化只读工具（get_slow_queries / get_connection_stats）
底层使用只读数据库账号兜底
```

### 七、K8s 工具安全设计示例

```text
ServiceAccount RBAC 最小权限
namespace 白名单
禁止任意 shell / exec
日志行数限制 + 时间窗口限制
日志敏感信息脱敏
写操作（restart/scale/rollback）必须进入审批节点
生产环境禁止自动 restart
```

## 高频追问

1. Tool Runtime 和普通 API Gateway 有什么区别？
2. 为什么不能让大模型直接查 MySQL/调 K8s API？
3. 如果 Agent 生成了一个危险操作，你的系统在哪里拦截？
4. 如何防止 Agent 绕过 Tool Runtime 直接调用底层 API？

## 我的回答要点

> 工具标准化的核心不是"把 SDK 接进来"，而是把每个基础设施能力包装成同一种工具协议：统一入参、统一权限、统一返回、统一审计、统一风险等级。Agent 不直接调用 K8s/MySQL/ALB/OSS，而是通过 Tool Runtime 提交工具调用请求，Runtime 负责权限校验、参数校验、超时重试、脱敏、审计和证据标准化。这样做的价值是：一方面让 Agent 能稳定使用多源运维数据，另一方面避免模型直接接触生产系统，把不可控的大模型调用变成可控、可审计、可回滚的运维流程。
