# 5.8 Evaluation

> 所属分支：[[05-Agent系统化落地层/_index|05-Agent系统化落地层]]

## 子节点 / 待填充要点
- 离线评测：Golden Dataset 评测、Bad Case 回归、LLM-as-Judge、结构化输出校验
- 在线评估：线上任务指标监控、用户采纳率、人工修正率
- 任务成功率：Agent 整体任务完成比例
- 节点成功率：单个节点执行成功率
- 工具调用成功率：工具执行成功比例
- 首次通过率：无人工介入的成功执行比例
- 人工介入率：需要人工干预的任务比例
- 恢复成功率：从 checkpoint 恢复后成功完成的比例
- 误执行率：Agent 执行了不应执行的动作的比例
- Bad Case 归因：失败节点定位、根因归类、修复策略
- 回归测试：Prompt 改动回归、模型切换回归、工具变更回归、RAG 更新回归

## 一句话定义

可评测 = 用一套固定 Case 和指标体系，持续判断 Agent 每次 Prompt、Planner、工具策略或 RAG 调整后有没有真正变好，而不是凭感觉判断。

## 解决什么问题

传统系统（API/单测/E2E）有确定性输出可评，但 Agent 输出不确定，同一个工单可能每次产出不同的排查路径和结论。不建立评测体系就无法回答：

```text
这次改 Prompt 后根因命中率有无提升？
排查计划有没有漏查关键证据源？
工具选择是否合理？
换模型后有没有退化？
```

## 如何实现

### 一、运维 Agent 四层评测体系

#### 第一层：工单结构化准确率

| 指标 | 说明 |
|------|------|
| service 抽取准确率 | 是否从工单正确识别服务名 |
| env 抽取准确率 | prod/staging/test 是否识别正确 |
| severity 抽取准确率 | P0/P1/P2/P3 分级是否准确 |
| symptom 分类准确率 | http_5xx / timeout / pod_crash / mysql_slow_query 分类是否正确 |
| timeRange 抽取准确率 | 时间窗口抽取是否正确 |

#### 第二层：流程质量评测

| 指标 | 说明 |
|------|------|
| 分诊准确率 | 故障类型（incidentType）分类是否正确 |
| 排查计划覆盖率 | 实际覆盖证据源 / 期望覆盖证据源 |
| 工具选择准确率 | 计划步骤匹配的工具是否合理 |
| 无效工具调用率 | 调用了与排查目标无关的工具占比 |
| 重复工具调用率 | 同一工具在同一 run 内重复无效调用 |

#### 第三层：根因与决策评测

| 指标 | 说明 |
|------|------|
| 根因 Top1 命中率 | 第一位候选根因是否命中标准答案 |
| 根因 Top3 命中率 | 前三位候选根因是否包含标准答案 |
| 风险等级准确率 | P0/P1/P2/P3 风险判断是否准确 |
| 处置建议可执行率 | 建议是否具体、有步骤、有风险说明、有回滚方案 |
| RCA 质量评分 | 时间线完整性、证据引用充分性、改进建议具体性 |

#### 第四层：在线业务指标

| 指标 | 说明 |
|------|------|
| 人工接管率 | 需要人工干预的任务比例 |
| 平均定位耗时 | 从工单创建到根因确认的时间 |
| 用户采纳率 | Agent 处置建议被运维人员采纳的比例 |
| 高风险动作拦截率 | 危险操作被审批流程正确拦截的比例 |

### 二、三层评测体系

```text
Layer 1：节点级评测 — 单独评某个节点（triage/planner/tool_router），定位问题快
Layer 2：链路级评测 — 评整条链路（工单→分诊→计划→工具→诊断→RCA），接近真实使用
Layer 3：在线评测 — 系统上线后看真实业务指标（人工接管率、平均耗时、用户采纳率）
```

### 三、离线评测集设计

最小可落地：10~20 个典型故障 Case，每个 Case 包含：

```json
{
  "caseId": "order_5xx_mysql_connection",
  "ticket": {
    "title": "订单接口 500 增多",
    "description": "14:20 开始用户无法下单，order-service 5xx 升高"
  },
  "expected": {
    "incidentType": "http_5xx",
    "service": "order-service",
    "expectedEvidenceCategories": ["alb_metrics", "k8s_pod_status", "mysql_connection", "app_logs"],
    "rootCause": "mysql_connection_exhausted",
    "riskLevel": "P1"
  }
}
```

工具返回用 fixture 固定（不真实调生产），保证每次评测结果可复现。

### 四、Eval Report 结构

```json
{
  "summary": {

    "rootCauseTop3Accuracy": 0.85,

    }
  ]

```

### 五、Bad Case 归因闭环

每次评测失败要能输出：

```text
失败 case → 期望结果 vs 实际结果 → 失败节点 → 可能原因 → 建议修复方向
```

例如：`alb_backend_unhealthy` case 失败 → failedNode=planner → 期望调用 alb.get_backend_health，实际只调了 k8s → 建议补充 http_5xx 场景下 ALB backend health 必查规则。

## 高频追问

1. 怎么保证评测集的代表性？case 从哪来？
2. 如果 Agent 输出和标准答案不一样，但也是合理答案，怎么评？
3. 评测指标很多，你们最关注哪几个？为什么？

## 我的回答要点

> Agent 的可评测核心不是"看它回答得像不像"，而是用固定工单、固定工具返回和标准答案评估它有没有变好。对运维智能体，我会把评测拆成四层：工单结构化准确率、流程质量（分诊/计划覆盖率/工具选择）、根因与决策（Top1命中率/风险等级）、在线业务指标（人工接管率/平均耗时）。通过离线评测集（10-20个典型Case + 工具fixture），每次修改 Prompt/Planner/Tool Router/RAG 后自动回放，输出根因命中率、计划覆盖率、工具选择准确率等指标，并记录 Bad Case 形成迭代闭环。
