# 8.1 研发流程

> 所属分支：[[08-工程交付层✅/_index|08-工程交付层]]

## 子节点 / 待填充要点
- AI Coding 接入 CI/CD
- 部署架构设计
- 发布门禁
- Runner 安全

## 一句话定义
AI Coding 应作为代码变更的生产者，无缝接入现有研发流程，接受与人工提交同等的质量门禁和发布管控。

## 解决什么问题
AI 生成代码不能绕过研发流程，需要和人的代码走同一条 CI/CD 流水线，确保质量一致性。

## 如何实现

### CI/CD 集成链路
```text
需求/Issue → Spec 生成 → Agent 执行代码修改 → 本地 Runner 验证
  → 生成 MR → CI 执行 lint/test/build → AI Review 输出风险说明
  → 人工合并 → 灰度发布 → 线上监控 → Bad Case 回流
```

### 平台部署架构设计
| 服务 | 部署方式 |
|------|----------|
| Web 前端 | 静态资源 / CDN / 内部门户 |
| Platform API | Node / NestJS 服务 |
| LLM Gateway | 统一模型调用、流式处理 |
| Orchestrator | Agent 编排服务 |
| Runner / Sandbox | 独立容器，限制权限 |
| MySQL | 平台控制面数据库 |
| PostgreSQL / Supabase | 用户业务数据 |
| Redis | 队列、缓存、锁、任务心跳 |
| OSS / 对象存储 | 代码包、截图、日志、预览产物 |
| Observability | 日志、trace、指标 |

### 关键设计原则
- AI 提交和人提交遵循同一套质量标准
- 发布必须走门禁（lint → tsc → test → build → review）
- Runner 容器隔离：限制 CPU、内存、文件系统和网络权限
- 高风险操作（部署、删除）需人工审批

## 项目映射
- 应用生成平台部署：平台 API → LLM Gateway → Orchestrator → Runner 四层
- AI Coding 工具包：本地 Runner → CI → MR → 人工合并

## 高频追问
1. 怎么把 AI Coding 接入 CI/CD？
2. 如果让你部署这个平台，怎么设计架构？
3. Runner 执行 AI 生成代码有什么安全风险？

## 我的回答要点
> AI Coding 不能绕过现有研发流程。它应该接入 CI/CD，作为代码变更的生产者，同时仍然接受 lint、测试、构建、代码审查和发布门禁。生产部署时，把平台 API、LLM Gateway、Agent Orchestrator、Runner、数据库和对象存储拆开。Runner 要特别隔离，因为它会执行代码和命令，必须限制 CPU、内存、文件系统和网络权限。
