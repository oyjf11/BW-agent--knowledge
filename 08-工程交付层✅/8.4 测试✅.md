# 8.4 测试

> 所属分支：[[08-工程交付层✅/_index|08-工程交付层]]

## 子节点 / 待填充要点
- AI 生成代码验证链路
- Playwright 测试失败归因
- TDD / BDD 在 AI Coding 中的应用
- Run 后自检机制

## 一句话定义
AI 生成代码必须经过可执行验证链路（lint → tsc → test → build → review），Playwright 是前端页面的关键验证手段。

## 解决什么问题
AI 生成代码不能靠肉眼看。需要通过自动测试验证真实交互路径，并区分测试失败是代码问题还是用例问题。

## 如何实现

### 验证链路
```text
代码生成 → 静态检查（ESLint / Prettier）→ 类型检查（TypeScript）
  → 单元测试（Vitest）→ E2E（Playwright）→ 构建验证（npm run build）
  → 代码审查（规则 + AI Review）→ 自测报告
```

### Playwright 失败归因矩阵
| 证据 | 可能原因 | 归因方向 |
|------|----------|----------|
| 页面白屏 | 代码运行错误 | 代码问题 |
| console error | JS 异常 | 代码问题 |
| network 404/500 | 接口或 mock 问题 | 环境/用例问题 |
| selector 找不到 | 页面没渲染或选择器错 | 需结合截图判断 |
| 截图正常但断言失败 | 断言文案或业务预期错 | 用例问题 |
| 点击无效 | 遮罩、disabled、异步状态 | 代码/时序问题 |
| 超时 | 时序问题、接口慢、等待条件错误 | 用例/环境问题 |

### TDD 实践
```text
先根据 Spec 生成测试 → 测试审核 → AI 生成实现 → 运行测试 → 失败修复
```
- 测试相当于可执行验收标准
- AI 必须以通过测试为生成目标

### BDD 实践
> Given 当前用户已登录
> When 点击导出按钮
> Then 应生成导出任务并展示成功提示

## 项目映射
- 应用生成平台 QA 阶段：lint → tsc → build → Sandpack 运行验证
- AI Coding 工具包：Runner 收集错误日志、截图、trace、console、network

## 高频追问
1. AI 生成代码后怎么验证？
2. Playwright 测试失败，怎么判断是代码错还是用例错？
3. TDD / BDD 在 AI Coding 中怎么做？

## 我的回答要点
> 我不会直接把测试失败归因给代码。会结合截图、trace、console、network、DOM snapshot 和测试日志判断。如果是 selector 不稳定，可能要修测试；如果是页面状态不对或 JS 报错，就回到代码修复。归因结果也会沉淀为 Bad Case。
