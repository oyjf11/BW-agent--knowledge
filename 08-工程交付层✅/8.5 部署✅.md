# 8.5 部署

> 所属分支：[[08-工程交付层✅/_index|08-工程交付层]]

## 子节点 / 待填充要点
- 平台部署架构
- Runner 安全隔离
- 灰度发布与回滚
- 运维 Agent 安全部署

## 一句话定义
AI Agent 平台部署需分层隔离，特别是 Runner 因执行 AI 生成代码，必须放在受限容器中，限制命令、网络、文件系统和资源。

## 解决什么问题
AI 生成代码不可信，直接在宿主机执行存在安全风险。需要沙箱隔离保证平台安全。

## 如何实现

### 部署架构分层
| 服务 | 部署方式 | 隔离要求 |
|------|----------|----------|
| Web 前端 | 静态资源 / CDN / 内部门户 | 标准 |
| Platform API | Node / NestJS 服务 | 标准 |
| LLM Gateway | 统一模型调用、流式处理 | 标准 |
| Orchestrator | Agent 编排服务 | 标准 |
| Runner / Sandbox | 独立容器 | **高隔离** |
| MySQL | 平台控制面数据库 | 内网 |
| PostgreSQL / Supabase | 用户业务数据 | RLS |
| Redis | 队列、缓存、锁、任务心跳 | 内网 |
| OSS / 对象存储 | 代码包、截图、日志 | 权限控制 |
| Observability | 日志、trace、指标 | 标准 |

### Runner 安全风险与对策
| 风险 | 控制 |
|------|------|
| 删除文件 | 命令白名单、工作目录隔离 |
| 读取密钥 | secret 脱敏、禁止访问敏感路径 |
| 恶意依赖 | 依赖白名单 |
| 网络外连 | 网络限制 |
| 无限循环 | 超时和资源限制 |
| 越权操作 | 租户隔离、权限校验 |
| 破坏环境 | 容器隔离 |
| 误部署 | 人工审批、灰度、回滚 |

### 关键原则
- Runner 不能直接在宿主机跑
- 命令白名单 + 工作目录隔离
- CPU、内存、文件系统、网络限制
- 高风险操作 dry-run 或人工确认

## 项目映射
- 应用生成平台：Runner 容器隔离执行代码生成和构建
- 运维 Agent：写操作人工审批 + 受控执行

## 高频追问
1. Runner 执行 AI 生成代码有什么安全风险？
2. 如果让你部署这个 AI 应用生成平台，怎么设计？
3. 运维 Agent 为什么不能全自动执行？

## 我的回答要点
> AI 生成代码不能直接在宿主机跑。Runner 应该放在受限容器或沙箱里，限制命令、网络、文件系统和资源。高风险操作必须 dry-run 或人工确认。生产部署时把平台 API、LLM Gateway、Agent Orchestrator、Runner 拆开，任务状态和版本记录放 MySQL，大文件产物放对象存储。
