# 10.4 工具安全

> 所属分支：[[10-安全与治理层✅/_index|10-安全与治理层]]

## 子节点 / 待填充要点
- 动态建表风险控制
- Runner 安全隔离
- SQL 注入防护
- 依赖白名单

## 一句话定义
AI 生成代码执行和动态数据库操作需要多层安全防护：Schema 白名单 → 模板生成 SQL → dry-run → 自动 RLS → Runner 容器隔离。

## 解决什么问题
AI 输出不可控，直接执行生成的 SQL 或代码存在安全风险，需要从生成阶段到执行阶段全程约束。

## 如何实现

### 动态建表安全矩阵
| 风险 | 控制方式 |
|------|----------|
| SQL 注入 | 不直接拼用户输入，Schema 白名单生成 |
| 表名混乱 | 统一命名规则 |
| 字段类型错误 | 类型枚举限制 |
| 缺少 tenant_id | 建表模板强制注入 |
| 缺少 RLS | 建表后强制启用 RLS |
| 重复建表 | MySQL 记录 schema_version |
| 破坏旧数据 | 迁移前 diff 和备份 |
| SQL 执行失败 | dry-run / transaction / rollback |
| 字段删除风险 | 默认禁止自动删除字段 |

### Runner 安全隔离
| 风险 | 控制 |
|------|------|
| 删除文件 | 命令白名单、工作目录隔离 |
| 读取密钥 | secret 脱敏、禁止访问敏感路径 |
| 恶意依赖 | 依赖白名单 |
| 网络外连 | 网络限制 |
| 无限循环 | 超时和资源限制 |
| 越权操作 | 租户隔离、权限校验 |
| 破坏环境 | 容器隔离 |
| 误部署 | 人工审批、灰度、回滚 |

### 安全设计原则
- 不让模型自由写任意 SQL → 先约束成 Schema → 模板生成 SQL
- 所有业务表强制带 tenant_id → 建表后自动开启 RLS
- 增量迁移默认只允许新增表和新增字段
- 删除字段、改字段类型等高风险操作需人工确认
- AI 生成代码不能在宿主机直接执行 → 容器沙箱隔离

## 项目映射
- 应用生成平台：Schema → SQL 模板 → dry-run → 执行 → RLS 自动注入
- AI Coding：Runner 容器隔离，命令白名单，网络限制

## 高频追问
1. 动态建表怎么保证安全？
2. AI 执行 SQL 怎么防注入？
3. Runner 执行代码有什么安全风险？

## 我的回答要点
> 动态建表的核心风险是模型输出不可控，所以我们不让模型自由写任意 SQL，而是先约束成 Schema，再由平台模板生成 SQL。所有业务表强制带 tenant_id，建表后自动开启 RLS。增量迁移默认只允许新增表和新增字段，高风险操作需要人工确认。Runner 必须放在受限容器中，限制命令、网络、文件系统和资源。
