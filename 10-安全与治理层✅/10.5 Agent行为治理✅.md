# 10.5 Agent行为治理

> 所属分支：[[10-安全与治理层✅/_index|10-安全与治理层]]

## 子节点 / 待填充要点
- 运维 Agent 不可全自动的原因
- 只读优先原则
- 审批粒度设计
- Agent 越权防护
- Bad Case 治理

## 一句话定义
Agent 行为治理是对 AI 执行边界的系统性约束，包括权限分级、操作审计、人审批和失败回溯，确保 Agent 只做被允许的事且可追溯。

## 解决什么问题
Agent 可能越权操作、错误执行、误删数据。需要系统性的行为约束和审计机制。

## 如何实现

### 行为治理维度
| 维度 | 控制方式 |
|------|----------|
| 权限分级 | 只读 / 建议 / 执行 / 管理 四级 |
| 操作审批 | 写操作、高危操作必须人工确认 |
| 执行边界 | target_files + allowed_changes 限定修改范围 |
| 审计追溯 | 所有操作落日志、记录操作人和时间 |
| 失败回滚 | dry-run / transaction / 版本快照 |
| Bad Case | 失败归因 → 分类 → 知识回流 |

### 运维 Agent 为什么不能全自动
- 运维场景涉及生产系统，错误动作可能造成事故
- Agent 可以做证据收集、根因假设、处置建议
- 但重启、扩容、回滚、删除、配置变更等写操作必须人工审批
- 设计原则：只读证据优先 → 建议生成 → 人工审批 → 受控执行 → 验证 → RCA

### 应用生成 Agent 行为治理
- Planner 输出 target_files 和 allowed_changes
- Codegen 只能在限定范围内修改
- Git diff / 文件白名单检查
- 默认禁止删除字段、修改字段类型
- QA 阶段执行完整验证链路

## 项目映射
- 应用生成平台：Router → Planner → Codegen → QA 多层边界约束
- 运维 Agent：人审批 → 模拟执行 → 受控执行 → 审计

## 高频追问
1. 运维 Agent 为什么不能全自动执行？
2. Agent 越权怎么办？
3. 如果 Agent 诊断错了怎么办？

## 我的回答要点
> Agent 行为治理的核心是"能做的不等于该做的"。我们通过权限分级、操作审批、执行边界和审计追溯，确保 Agent 的行为在可控范围内。运维 Agent 特别强调只读优先和人工审批，因为生产系统不容出错。应用生成 Agent 通过 target_files 和 allowed_changes 限定修改范围，再通过 diff 和 QA 校验是否越界。
