# 13.1 Durable Execution

> 所属分支：[[13-Agent Runtime深水区✅/_index|13-Agent Runtime深水区]]

## 子节点 / 待填充要点
- Durable Execution 定义与核心价值
- Checkpoint 如何支撑 Durable Execution
- 执行流程（执行前/成功后/失败/审批暂停）
- LLM 上下文恢复的边界
- Checkpoint 在 Agent Runtime 中的架构位置

## 一句话定义

Durable Execution 是保证 Agent 长流程任务不因服务重启、工具失败或人工审批暂停而丢失执行状态的能力，核心通过 Checkpoint + 状态持久化 + 节点级恢复实现。

## 解决什么问题

Agent 不是一次请求返回，而是多步骤长链路：接收任务 → 分析意图 → 制定计划 → 调工具 A → 调工具 B → 汇总证据 → 生成判断 → 等人工审批 → 执行动作 → 验证结果 → 生成报告。

中间任何一步都可能失败：LLM 调用超时、工具接口失败、网络断开、服务重启、人工审批迟迟未返回、Worker 被重启。

**没有 Durable Execution**：只能从头重跑整个链路。
**有 Durable Execution**：从上一次成功节点继续，不重复执行已完成步骤。

Durable Execution 解决的不是模型能力问题，而是**工程可靠性问题**，包括五个核心维度：

| 维度 | 说明 |
|------|------|
| **resumability** | 断点续跑，服务重启或工具失败后从最近稳定节点恢复 |
| **idempotency** | 高风险动作通过幂等键防止重复执行（重启、回滚、扩容等） |
| **human-in-the-loop** | 审批暂停后状态持久化，审批回来不丢上下文 |
| **auditability** | 每个节点的输入/输出/判断依据可追溯，支撑复盘和 RCA |
| **replayability** | 结合 Event Log 可回放完整执行过程，用于 Bad Case 分析和离线评估 |

## 如何实现

### 核心理念

Checkpoint 本质是把 Agent 从"内存里的对话流程"升级成**可持久化的任务状态机**。

### 执行流程

每个关键节点执行前后都保存 checkpoint：

```
执行前：准备执行 collect_evidence 节点
  → 保存 current_node = collect_evidence, status = running

执行成功后：collect_evidence 执行完成
  → 保存 evidence 结果，current_node = diagnosis

执行失败后：collect_mysql_metrics 失败
  → 保存 failed_node, error, status = failed

人工审批暂停：生成处置建议
  → 进入 approval 节点，status = waiting_approval
  → 审批通过后：status = running, current_node = execution，继续执行
```

核心逻辑就三句：**执行前保存 → 执行后保存 → 失败时保存**。

### 伪代码

```ts
async function runAgent(taskId: string) {
  let checkpoint = await loadCheckpoint(taskId);

  while (checkpoint.status !== "completed") {
    const node = getCurrentNode(checkpoint.currentNode);

    try {
      // 执行前保存
      await saveCheckpoint({
        ...checkpoint,
        status: "running",
        currentNode: node.name
      });

      const output = await node.execute(checkpoint.state);

      // 执行后保存
      checkpoint = {
        ...checkpoint,
        state: { ...checkpoint.state, ...output },
        currentNode: node.next,
        status: node.next ? "running" : "completed"
      };

      await saveCheckpoint(checkpoint);
      await appendEvent(taskId, node.name, "success", output);

    } catch (error) {
      // 失败时保存
      await saveCheckpoint({
        ...checkpoint,
        status: "failed",
        error: serializeError(error)
      });
      await appendEvent(taskId, node.name, "failed", { error });
      throw error;
    }
  }
}
```

### 失败重试：节点级而非全链路

没有 checkpoint 的失败重试是整个任务重跑。有 checkpoint 后可以做到**节点级重试**：

```
Node 1：parse_ticket ✅
Node 2：collect_k8s_status ✅
Node 3：collect_mysql_metrics ❌
Node 4：diagnosis 未执行

恢复时只从 Node 3 开始，不重跑 Node 1-2。
```

这对生产系统尤其重要，因为有些动作不能重复执行（重启服务、扩容实例、修改配置、发通知、建表）。这些动作必须配备：执行前 checkpoint + 执行后 checkpoint + 幂等校验 + 执行记录。

### LLM 上下文恢复

Checkpoint **不能**恢复模型内部的隐状态（模型本身无状态），但**可以**恢复外部任务状态：用户输入、历史消息摘要、计划、工具结果、证据链、中间结论。恢复时重新构造 prompt，让 LLM 基于保存的上下文继续执行。

真正恢复的是 Agent Runtime 里的外部状态，而非模型内部状态。

### Checkpoint 在 Agent Runtime 架构中的位置

```text
Agent Runtime
├── Task State Machine       ← 任务状态建模
├── Checkpoint               ← 状态快照持久化（本节核心）
├── Event Log                ← 历史过程追踪
├── Tool Executor            ← 工具调用执行
├── Retry / Timeout          ← 失败恢复
├── Human Approval           ← 人工审批暂停续跑
├── Permission Control       ← 权限校验
├── Verification             ← 执行结果验证
└── Replay / Evaluation      ← 回放与离线评估
```

Checkpoint 是 Agent Runtime 为了支持 Durable Execution 而提供的状态持久化机制。它不是模型层能力，而是 Agent 工程化和生产化能力。

## 项目映射

- **运维智能体**：工单诊断流程从分诊、证据采集、根因分析、处置建议、人工审批、执行验证到 RCA，每个关键节点都落 checkpoint，支撑可恢复、可追踪、可审计。详见 [[25.1 核心链路✅|运维核心链路]]。
- **应用生成智能体**：代码生成流程从 Router、Planner、Codegen 到 QA 和部署，每个节点 checkpoint 保证副作用不重复执行。详见 [[22.5 多Agent风险|多 Agent 风险控制]]。

## 高频追问

1. Durable Execution 和 Checkpoint 是什么关系？
2. Checkpoint 能不能恢复 LLM 的上下文？
3. 每一步都 checkpoint 吗？什么时候保存？
4. 执行成功但 checkpoint 保存失败怎么办？

## 我的回答要点

> Checkpoint 解决的是 Agent 长流程执行中的状态持久化和断点续跑问题。Agent 不是一次性请求，它经常经历规划、工具调用、证据收集、人工审批、执行验证等多个节点。中间如果服务重启、工具失败、审批挂起，没有 checkpoint 就只能从头跑。Checkpoint 在关键节点保存当前任务状态、已完成步骤、工具结果、中间判断和下一步动作，让 Agent 可以从失败点或审批点继续执行。同时它也提供审计基础，方便追踪 Agent 为什么这么判断、执行过什么、后续如何复盘和评估。

> 落到项目里，运维智能体的每个关键节点（分诊、证据采集、根因分析、处置建议、审批、执行、验证、RCA）都要打 checkpoint，保证工单诊断流程的可恢复和可审计；应用生成智能体在 Codegen、SQL、部署等副作用节点前后打 checkpoint，防止重复建表、重复写文件。
