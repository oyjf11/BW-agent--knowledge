# 13.3 幂等与去重

> 所属分支：[[13-Agent Runtime深水区✅/_index|13-Agent Runtime深水区]]

## 子节点 / 待填充要点
- action_id 设计
- idempotency_key 设计
- task_id + node_id 去重
- 执行前查重
- 执行后记录
- Checkpoint 与幂等的配合

## 一句话定义

幂等与去重是 Agent 防止高风险动作重复执行的安全机制，通过 action_id + idempotency_key + 执行前置校验 + 执行记录，保证同一个操作不会被重试机制意外执行两次。

## 解决什么问题

Agent 重试机制（节点失败重试、服务重启恢复）可能触发重复执行不可逆操作：

- 重启服务 → 服务已经被重启一次，重试可能二次重启造成中断
- 扩容实例 → 可能重复扩容
- 修改配置 → 可能覆盖正确的回滚配置
- 创建工单 → 可能产生重复工单
- 发送通知 → 可能重复打扰
- SQL 建表 → 可能重复执行 DDL 导致报错

没有幂等控制，Agent 可能因为重试造成**二次事故**。Checkpoint 解决恢复问题，幂等解决重复执行风险，两者必须配合使用。

## 如何实现

### 核心机制

每个有副作用的操作（写操作、执行动作）必须携带：

| 字段 | 作用 | 示例 |
|------|------|------|
| `action_id` | 本次操作的唯一标识 | `rollback-order-service-v32-to-v31` |
| `idempotency_key` | 业务级幂等键，相同操作共享同一 key | `ticket_9527:rollback:v1.2.7` |
| `task_id + node_id` | 任务级去重，同一任务同一节点不会重复执行 | `INC-001:execution` |

### 执行流程

```text
执行前：
  - 检查 idempotency_key 是否已存在 → 如果存在且成功，跳过执行
  - 检查 task_id + node_id 是否已有成功记录 → 如果有，跳过执行
  - 保存 input_hash 到 checkpoint
  - 保存状态为 RUNNING

执行后：
  - 保存 output_hash 到 checkpoint
  - 保存状态为 SUCCESS
  - 记录 action_id + idempotency_key 执行记录
  - 保存 artifact_refs

恢复时：
  - 如果 checkpoint 状态为 SUCCESS 且 output_hash 匹配 → 跳过
  - 如果 checkpoint 状态为 RUNNING 且超时 → 检查实际是否已执行，决定重试或跳过
  - 如果 checkpoint 状态为 FAILED 且 retry_count < max_retry → 重试
```

### 幂等记录表设计

```sql
CREATE TABLE action_executions (
  action_id         VARCHAR(128) PRIMARY KEY,
  task_id           VARCHAR(64),
  idempotency_key   VARCHAR(128),
  node_name         VARCHAR(64),
  status            VARCHAR(32),   -- pending / executing / success / failed
  input_hash        VARCHAR(64),
  output_hash       VARCHAR(64),
  created_at        TIMESTAMP,
  updated_at        TIMESTAMP
);

CREATE UNIQUE INDEX idx_idempotency_key ON action_executions(idempotency_key);
CREATE INDEX idx_task_node ON action_executions(task_id, node_name);
```

### 边界场景

**执行成功但 checkpoint 保存失败**：这是最难处理的情况。处理策略：

1. 执行前先打一条 `pending` 状态的 action_executions 记录
2. 执行成功后更新为 `success`
3. 恢复时如果 checkpoint 丢失，查询 action_executions 表——如果 `status = success`，说明已执行，跳过重试
4. 对于特别关键的操作（重启、回滚），结合外部系统状态做二次确认（如查询 K8s pod 当前状态）

**幂等 + Checkpoint 的关系**：

> Checkpoint 回答"执行到哪了"，Idempotency 回答"这个动作执行过了吗"。Checkpoint 负责流程级状态，Idempotency 负责操作级去重。两者配合：Checkpoint 确定从哪个节点恢复，Idempotency 确定该节点是否已经执行过，避免重复操作。

## 项目映射

- **应用生成智能体**：SQL 建表脚本已成功但后续预览失败 → 恢复时不重新建表，查询 action_executions 确认 MIGRATION_APPLIED 状态 → 从预览步骤继续。详见 [[22.5 多Agent风险#SQL 脚本重复执行|22.5 多 Agent 风险]]。
- **运维智能体**：执行动作（重启、回滚、扩容）前后打 checkpoint + action_id 校验 → 避免 Worker 重启或审批超时后重复触发写操作。详见 [[25.4 安全控制✅|25.4 安全控制]]。

## 高频追问

1. 执行成功但 checkpoint 保存失败怎么办？怎么保证一致性？
2. idempotency_key 怎么设计？用业务 ID 还是生成 UUID？
3. 如果重试时外部系统状态已经变了，怎么判断要不要再执行？
4. 幂等和分布式锁的区别？

## 我的回答要点

> 对高风险动作，不能只依赖 checkpoint 做恢复，还要结合 action_id、幂等键、执行前置校验和执行记录。每个执行动作生成唯一 action_id，执行前检查这个 action_id 是否已经成功执行过，避免因为重试造成重复操作。Checkpoint 解决恢复问题，Idempotency 解决重复执行风险，两者配合使用。

> 落到项目里，运维智能体在审批、执行、验证前后强制打 checkpoint，同时每个执行动作带幂等键，恢复时先查执行记录再决定是否重试；应用生成智能体的 SQL 建表、文件写入、部署等副作用节点同样带幂等键，防止重试导致重复建表或覆盖文件。
