# 13.4 并发控制

> 所属分支：[[13-Agent Runtime深水区✅/_index|13-Agent Runtime深水区]]

## 子节点 / 待填充要点
- asyncio.gather 并行调度
- 时间预算优先于轮次
- 单 Agent 超时 vs fanout 总超时
- 动态超时分配

## 一句话定义

Agent 并发控制的核心不是简单地并行调用，而是在有限的时间预算内，动态分配超时给每个并行任务，保证总 fanout 在截止时间内必然返回。

## 解决什么问题

多个 Agent 并行执行时，如果某个 Agent 耗时过长或无响应，会阻塞整个 fanout，导致下游节点迟迟收不到结果。需要精细的并发控制和超时预算来保证系统响应时间。

## 如何实现

### 核心原则：时间预算优先于轮次

Agent 的 ReAct 循环不按"最多 N 轮"控制，而是按"剩余时间"控制。每轮前检查 `deadline - now()`，< 2s 强制退出。即使 LLM 返回 tool_calls，超时也强制截断并标记 `truncated=True`。

### 多级超时预算表

| 层级 | 预算 | 机制 |
|------|------|------|
| 单 Agent | 30s | `AgentTask.timeout_ms=30000` |
| LLM 单次调用 | min(15s, 剩余时间) | `asyncio.wait_for(timeout=...)` |
| 单工具调用 | min(30s, 剩余预算/tool_count) | 动态分配 |
| fanout 总 | 60s | `asyncio.wait_for(gather(...), timeout=60)` |

### 并行调度

```python
# 5 个 Specialist Agent 并发执行
fanout_tasks = [agent.run(agent_task) for agent in pool.values()]
results = await asyncio.wait_for(
    asyncio.gather(*fanout_tasks, return_exceptions=True),
    timeout=60.0
)
```

每个 Agent 内部独立做时间管理，最外层 fanout 做总超时兜底。`return_exceptions=True` 保证单个 Agent 失败不拖垮整体。

### Agent 内部的动态超时分配

```python
remaining = deadline - time.monotonic()
if remaining < 2.0:
    return truncated_result  # 强制截断

llm_timeout = min(15.0, remaining * 0.6)  # LLM 拿剩余时间的 60%
tool_timeout = min(30.0, (remaining - llm_timeout) / max(tool_count, 1))
```

关键设计点：
- LLM 调用拿剩余时间的 60%，工具调用分剩余的 40%
- 每个超时值都用 `min()` 封顶，防止单次调用占用过多预算
- 时间优先于轮次：不保证完成所有 ReAct 轮次，只保证在时间内返回

### 降级时的并发处理

当部分 Agent 超时或失败时，aggregate 通过 `quality_score` 降权（partial→×0.5，failed→不计分），而非阻塞等待。这保证了"部分有用信息 > 没有信息"。

## 项目映射

- OpsPilot Specialist Agent Pool：5 个 Specialist Agent 通过 `asyncio.gather` 并发执行，单 Agent 30s 超时，fanout 总 60s 超时
- Agent 内部 ReAct 循环按时间预算动态分配每轮和每个工具调用的超时

## 高频追问

1. 如果 5 个 Agent 都超时了怎么办？
2. 时间预算和轮次预算哪个优先？为什么？
3. 怎么保证单个 Agent 不拖垮整体 fanout？

## 我的回答要点

> Agent 并发控制的核心是时间优先：不是按"最多 N 轮"控制，而是按"剩余时间"控制。每个 Agent 内部每轮开始前检查剩余时间，< 2s 强制截断。fanout 总超时 60s，用 `asyncio.gather` + `return_exceptions=True` 保证单个 Agent 失败不影响其他。降级时通过 quality_score 降权而非阻塞——宁可拿到部分结果，也不要什么都不返回。
