# 13.8 Agent状态建模

> 所属分支：[[13-Agent Runtime深水区✅/_index|13-Agent Runtime深水区]]

## 一句话定义

Agent 状态建模是把 Agent 任务执行抽象成可持久化的状态机，通过 task_id + current_node + status + state_json 来追踪任务当前状态，通过 event log 记录历史过程，使 Agent 从"内存里的对话流程"升级为"可恢复、可审计的持久化任务状态机"。

## 解决什么问题

初级 Agent Demo 的状态存在内存里（一个 JS 对象），服务重启就丢失。生产级 Agent 需要把状态落库，不依赖某个进程，成为可持久化的任务状态机。同时需要区分"当前状态"和"历史过程"两种不同维度的数据。

## 如何实现

### 任务抽象模型

一个 Agent 任务可抽象为五个核心要素：

```text
task_id       → 任务唯一标识
current_node  → 当前执行到哪个节点
status        → 任务状态（running / waiting_approval / failed / completed）
state         → 当前任务状态快照（用户输入、计划、工具结果、中间产物等）
events        → 历史执行过程（每一步的输入/输出/错误）
```

例如运维智能体的任务链路：

```text
工单接入 → 自动分诊 → 证据采集 → 根因分析 → 处置建议 → 人工审批 → 执行验证 → RCA
```

每走到一个节点，就落一次 checkpoint。

### Checkpoint 核心数据结构

```ts
type AgentCheckpoint = {
  taskId: string;
  currentNode: string;
  status: "running" | "waiting_approval" | "failed" | "completed";
  state: {
    userInput: string;
    plan?: AgentPlan;
    evidence?: Evidence[];
    diagnosis?: Diagnosis;
    remediationPlan?: RemediationPlan;
    approval?: ApprovalState;
    executionResult?: ExecutionResult;
  };
  retryCount: number;
  updatedAt: string;
};
```

运维智能体的 checkpoint 示例（WAITING_APPROVAL 节点）：

```json
{
  "taskId": "INC-20260531-001",
  "currentNode": "approval",
  "status": "waiting_approval",
  "state": {
    "ticket": {
      "title": "订单服务接口 500 异常",
      "service": "order-service"
    },
    "evidence": [
      { "source": "k8s", "summary": "order-service pod 出现 CrashLoopBackOff" },
      { "source": "mysql", "summary": "近 10 分钟错误率明显升高" }
    ],
    "diagnosis": {
      "rootCause": "新版本配置错误导致服务启动失败",
      "confidence": 0.82
    },
    "remediationPlan": {
      "action": "rollback_deployment",
      "riskLevel": "medium",
      "needApproval": true
    }
  }
}
```

### 数据库表设计

#### agent_tasks — 记录任务当前状态

```sql
CREATE TABLE agent_tasks (
  id              VARCHAR(64) PRIMARY KEY,
  task_type       VARCHAR(64),
  status          VARCHAR(32),
  current_node    VARCHAR(64),
  state_json      JSONB,
  retry_count     INT DEFAULT 0,
  created_at      TIMESTAMP,
  updated_at      TIMESTAMP
);
```

回答的问题：这个任务现在执行到哪里了？当前状态是什么？下一步该干什么？

#### agent_events — 记录过程事件

```sql
CREATE TABLE agent_events (
  id              BIGSERIAL PRIMARY KEY,
  task_id         VARCHAR(64),
  node_name       VARCHAR(64),
  event_type      VARCHAR(64),
  input_json      JSONB,
  output_json     JSONB,
  error_json      JSONB,
  created_at      TIMESTAMP
);
```

回答的问题：这个任务历史上发生过什么？调用过哪些工具？每一步输入输出是什么？哪里失败过？

### Checkpoint 存储内容清单

一个完整的 checkpoint 通常包含以下字段：

| 类型 | 内容 |
|------|------|
| 任务标识 | taskId、ticketId、userId、tenantId |
| 当前节点 | currentNode、status、nextNode |
| 用户输入 | 原始需求、工单内容、上下文 |
| 计划结果 | Agent plan、DAG、任务拆解 |
| 工具结果 | API 查询结果、日志、指标、数据库结果 |
| 中间产物 | diagnosis、evidence、remediationPlan |
| 人工审批状态 | approver、approvalStatus、approvalTime |
| 执行记录 | action、target、result、rollbackPlan |
| 验证结果 | healthCheck、metricsAfter、finalStatus |
| 错误信息 | error、retryCount、failedNode |
| 时间信息 | createdAt、updatedAt、finishedAt |

### Checkpoint vs Event Log 对比

| 对比项 | Checkpoint | Event Log |
|--------|-----------|-----------|
| 关注点 | 当前状态 | 历史过程 |
| 核心问题 | 现在执行到哪？ | 之前发生了什么？ |
| 作用 | 恢复、续跑 | 审计、回放、分析 |
| 数据形态 | 最新快照 | 追加日志 |
| 更新方式 | 覆盖更新（upsert） | append-only |
| 存储需求 | 读快写少 | 追加多 |

**两者关系**：Checkpoint = 当前快照，Event Log = 历史流水。生产级 Agent 通常两个都要——用 Event Log 记录过程，用 Checkpoint 保存可恢复状态。

### 保存粒度策略

不是每一步都 checkpoint，而是在**关键状态边界**保存：

```
高价值恢复点（打 Checkpoint）：
  任务开始、计划生成后、工具调用完成后、审批前、执行前、执行后、验证后、任务结束

低价值中间过程（仅打 Event Log）：
  LLM 流式输出的中间 token、工具调用的中间状态、RAG 检索的中间结果
```

面试表达：> 低价值中间过程用 event log，高价值恢复点用 checkpoint。

### 存储选型策略

| 存储 | 适合场景 |
|------|---------|
| Redis | 短任务、临时状态、高频读写、运行态缓存 |
| MySQL / PostgreSQL | 需要审计、恢复、长期保留的核心状态 |
| 文件 / 对象存储（OSS/S3） | 大型上下文、日志、长文本、模型输出归档 |
| Redis + DB 组合 | Redis 做运行态缓存，DB 做最终持久化 |

运维智能体这类生产级流程的核心状态要落 MySQL/PostgreSQL（支持审计和恢复）。对于日志、模型长输出、RCA 文档这类大对象，放对象存储，数据库只存索引和摘要。

## 项目映射

- **运维智能体**：每个关键节点（TICKET_RECEIVED → TRIAGE_DONE → EVIDENCE_COLLECTED → DIAGNOSIS_DONE → WAITING_APPROVAL → APPROVED → EXECUTED → VERIFIED → RCA_GENERATED）完成后打 checkpoint，run_id + step_id + node_key + status + state_json 完整记录。详见 [[22.5 多Agent风险#运维场景的特殊风险|22.5 运维场景]]。
- **应用生成智能体**：同样在 REQUEST_RECEIVED → ROUTER_DONE → CODEGEN_DONE → QA_PASSED → DEPLOYED 等节点打 checkpoint，防止副作用重复执行。详见 [[22.5 多Agent风险#应用生成场景的特殊风险|22.5 应用场景]]。

## 高频追问

1. Checkpoint 存数据库还是 Redis？什么时候用哪个？
2. 每一步都 checkpoint 吗？性能开销怎么控制？
3. Checkpoint 和 Event Log 有什么区别？什么场景用各自？
4. Checkpoint 能不能恢复 LLM 的上下文？

## 我的回答要点

> Agent 状态建模的核心是把任务执行抽象成状态机：每个任务有 task_id、current_node、status、state_json 等字段。每个关键节点执行前后保存 checkpoint，比如计划生成后、工具调用完成后、进入审批前、执行动作前后。恢复时根据 task_id 读取最近的 checkpoint，拿到 current_node 和 state_json，重新构造上下文，从对应节点继续执行。

> 同时把 checkpoint 和 event log 区分开——checkpoint 保存当前可恢复状态，event log 追加记录每一步发生过什么，用于审计、回放和 RCA。存储上，核心状态落 MySQL 支持审计和恢复，大对象（日志、RCA 文档）放对象存储，Redis 做运行态缓存。
