# 13.9 Agent Orchestrator

> 所属分支：[[13-Agent Runtime深水区✅/_index|13-Agent Runtime深水区]]

## 子节点 / 待填充要点
- 固定 Agent 池 vs Dynamic Orchestrator 选型
- Feature Flag 双路径路由
- 工具归属边界设计
- YAML 静态配置 vs DB 动态加载
- v2 双写兼容

## 一句话定义

Agent Orchestrator 不是让 LLM 动态决定调用哪个 Agent，而是通过固定 Agent 池 + Feature Flag 双路径路由，保证 v1 到 v2 的渐进式上线和无风险回退。

## 解决什么问题

Agent 编排的核心难题：如何在"全量调度 vs 按需调度""新路径 vs 旧路径"之间做安全切换，同时保证新增 Agent 不会破坏现有工作流。

## 如何实现

### 固定 Agent 池 vs Dynamic Orchestrator 选型

| 决策 | 选择 | 放弃 | 理由 |
|------|------|------|------|
| **Agent 池方案** | 5 个 fixed Specialist Agent 全量调度 | Dynamic Orchestrator（LLM 按需调度）、Supervisor Agent | v1 复杂度可控，全量调度保证覆盖度，固定 Agent 便于规则兜底 |
| **配置管理** | YAML 启动时硬编码加载 | DB 动态加载 | v1 不需要管理 API，配置变更走 code review 可追溯 |

不作为表达方向：固定 Agent 池意味着每次 fanout 都调度全部 5 个 Agent，即使某些 Agent 与当前故障类型无关。这是 v1 的妥协——减少 LLM 参与编排决策，用全量覆盖换确定性。

### Feature Flag 双路径路由

```python
# Feature Flag 控制新旧路径切换
flag_enabled = settings.AGENT_FEATURE_SPECIALIST_POOL

if flag_enabled:
    # v2 路径：SpecialistAgent pool
    agent_tasks = await _plan_agent_tasks(state)
    analyses = await _run_specialist_pool(agent_tasks)
else:
    # v1 路径：原 _collect_one
    evidence_items = await _collect_one(state)
```

三个关键设计点：

1. **节点级开关**：仅 planner / fanout / aggregate 读取 flag，不影响其他节点
2. **双写兼容**：v2 路径同时产出 v2 格式（agent_tasks + specialist_analyses）和 v1 格式（plan + evidence_items），保证 diagnose / rca 等下游节点无需改动
3. **零回归**：`flag=false` 时原路径完全不受影响

### 工具归属边界设计

5 个 Specialist Agent 各有一条独有工具链，`tool_names` 白名单互不相交：

| Specialist | 核心工具 | 边界澄清 |
|-----------|---------|---------|
| **K8s Specialist** | `query_k8s_pods`、`query_k8s_events`、`query_k8s_pod_logs_summary`、`query_k8s_deployment_status` | pod logs 是容器 stdout/stderr（K8s 视角），不是应用日志 |
| **Log Specialist** | `query_logs` | 集中式日志平台（应用视角），是应用日志唯一入口 |
| **DB Specialist** | `query_slow_queries`、`query_db_connections`、`query_db_metrics` | 数据库状态和性能指标 |
| **Metrics Specialist** | `query_metrics` | **唯一指标查询入口**；K8s Specialist 不查询指标 |
| **Deployment Specialist** | `query_deployments` | 发布系统变更历史（非 K8s Deployment 实时状态） |

关键边界澄清：
- `query_k8s_pod_logs_summary` → **K8s Agent**（容器 stdout/stderr，K8s 视角）
- `query_logs` → **Log Agent**（集中式日志平台，应用视角）
- `query_k8s_deployment_status` → **K8s Agent**（K8s Deployment 实时状态）
- `query_deployments` → **Deployment Agent**（发布系统变更历史）

### 运行时 guard：防止 LLM 幻觉

```python
if tool_name not in self.config.tool_names:
    # LLM 幻觉出不在白名单的工具名
    messages.append({"role": "tool", "content": f"Error: tool '{tool_name}' not available"})
    continue  # 不调 gateway，进入下一轮
```

初始化白名单校验 + 运行时 `_execute_tool()` 二次检查，防止 LLM 幻觉绕过初始化检查直接调用危险工具。

### Aggregator 的配置约定

SpecialistEvidence 的 `conclusion` 字段按固定前缀，aggregate 仅通过字符串前缀做分类匹配（不依赖 LLM 比对）：

| 前缀 | 含义 | aggregate 行为 |
|------|------|---------------|
| `正常:` | 无异常 | 正常纳入 |
| `异常:` | 有异常 | 用于矛盾检测 |
| `部分:` | 产出不完整 | 权重 ×0.5 |
| `失败:` | 完全失败 | 不计入评分 |

## 项目映射

- OpsPilot Specialist Agent Pool：Feature Flag `AGENT_FEATURE_SPECIALIST_POOL` 控制 v1/v2 路径切换，builder.py 零改动
- 5 个 Specialist Agent 的 tool_names 白名单互不相交，运行时 guard 防止 LLM 幻觉
- conclusion 前缀约定让 aggregate 的 `_detect_cross_agent_contradictions()` 仅通过字符串前缀做分类匹配

## 高频追问

1. 为什么选固定 Agent 池而不是 Dynamic Orchestrator？LLM 按需调度不应该更智能吗？
2. Feature Flag 怎么保证新增代码不影响旧路径？
3. 工具归属边界怎么划分？会不会有工具被两个 Agent 同时调用？

## 我的回答要点

> Agent 编排的核心选择是可控性 > 灵活性。我选择了固定 Specialist Agent 池全量调度而非 LLM 驱动的动态编排，原因是 v1 阶段复杂度可控、全量调度保证覆盖度、固定 Agent 便于规则兜底。Feature Flag 采用节点级开关 + 双写兼容——新路径同时产出旧格式，保证下游节点零改动。工具归属按数据视角严格划分，每个工具只有一个 Agent 入口，白名单互不相交，加上运行时 guard 防止 LLM 幻觉调用错误工具。Aggregate 通过 conclusion 前缀（正常:/异常:/部分:/失败:）做确定性分类匹配，不依赖 LLM 二次比对。
