# 20.8 RAG注入方式

> 所属分支：[[20-RAG深水区✅/_index|20-RAG深水区]]

## 子节点 / 待填充要点
- 应用生成平台中 RAG 存什么
- 代码 RAG vs 文档 RAG
- RAG 注入时机（Router / Planner / Codegen）

## 一句话定义
在应用生成平台中，RAG 不是普通知识库问答，而是给 Router、Planner 和 Codegen 注入项目上下文证据（页面元信息、Schema 历史、组件模板等），帮助 Agent 精准定位和生成。

## 解决什么问题
模型不知道当前项目结构、已有 Schema 和历史生成记录，容易生成不一致或越界的代码。RAG 提供精准上下文缩小生成范围。

## 如何实现

### RAG 数据资产
| 数据 | 用途 | 消费方 |
|------|------|--------|
| 页面元信息 | 定位目标页面 | Router |
| 路由信息 | 判断路径影响 | RoutingPlanner |
| Schema 历史版本 | 增量修改依据 | SupabasePlanner |
| 历史生成任务 | 相似场景参考 | Router / Planner |
| 平台规则 | 约束模型输出 | Codegen |
| 组件模板 | 保持风格一致 | UIPlanner / Codegen |
| Bad Case | 避免重复错误 | Planner / Codegen |
| 字段命名规则 | 生成一致字段 | SupabasePlanner |
| 企业规范 | 代码风格、权限规则 | Codegen |

### 代码 RAG vs 文档 RAG
| 对比 | 文档 RAG | 代码 / 项目 RAG |
|------|----------|-----------------|
| 分块 | 标题、段落 | 文件、组件、函数、路由、Schema |
| 检索 | 语义相似 | 语义 + 路径 + 符号 + import |
| 目标 | 回答问题 | 定位修改点 |
| 输出验证 | 答案忠实度 | 编译、测试、运行 |
| 风险 | 答案幻觉 | 改错文件、破坏依赖 |

### 上下文注入时机
- **Router**：页面元信息 → 判断目标页面和任务类型
- **Planner**：Schema 历史 + 组件模板 → 规划修改方案
- **Codegen**：组件模板 + 企业规范 → 保持风格一致

## 项目映射
> 比如用户说"给客户页加一个跟进状态"，Router 通过页面元信息知道目标页面，SupabasePlanner 通过 Schema 历史知道 customers 表已有字段，Codegen 通过组件模板保持风格一致。

## 高频追问
1. 你们应用生成平台里 RAG 存什么？
2. 代码 RAG 和文档 RAG 有什么区别？
3. RAG 怎样帮助 Router 判断任务类型？

## 我的回答要点
> RAG 在我们这里不是普通知识库问答，而是给 Router、Planner 和 Codegen 注入证据。代码 RAG 不能只按文本切 chunk，要保留文件路径、组件名、函数名、import/export、路由、Schema 关系。它的目标不是回答问题，而是帮助 Agent 精准定位该改哪里。
