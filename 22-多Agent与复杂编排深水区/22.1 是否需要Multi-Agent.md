# 22.1 是否需要Multi-Agent

> 所属分支：[[22-多Agent与复杂编排深水区/_index|22-多Agent与复杂编排深水区]]

## 子节点 / 待填充要点
- 什么时候需要 Multi-Agent
- 什么时候一个 Agent 就够了
- Multi-Agent 的核心价值
- 单 Agent vs 多 Agent 对比

## 一句话定义
Multi-Agent 不是"让多个大模型互相聊天"，而是把复杂任务拆成多个有边界的 Agent 节点，由统一调度器协调，每个 Agent 只负责一个确定环节。

## 解决什么问题
任务越复杂（涉及生成、校验、审批、部署等多环节），单一 Agent 越容易产生不可控输出、难以分步验证和断点恢复。Multi-Agent 通过职责拆分降低单点复杂度，提升可验证性和可恢复性。

## 何时需要 Multi-Agent

| 场景 | 建议 |
|------|------|
| 简单问答 / 知识检索 | 单 Agent 即可 |
| 多步骤业务流程（生成 + 校验 + 部署） | 需要 Multi-Agent |
| 需要不同权限边界（只读 vs 写操作） | 需要 Multi-Agent |
| 需要并行执行独立子任务 | 需要 Multi-Agent |
| 需要人工审批环节 | 需要 Multi-Agent |
| 产物需要分步验证和回滚 | 需要 Multi-Agent |

## 如何实现
不是所有 Agent 串行执行。合理的编排方式是 **任务依赖图 + 状态机**：

- **任务依赖图**：描述节点间的前后依赖和并行关系（哪些必须先做，哪些可以并行，哪些依赖前一步结果）
- **状态机**：记录每个节点当前状态（PENDING / RUNNING / SUCCESS / FAILED / WAITING_APPROVAL）

Orchestrator 根据当前状态和依赖关系决定下一步调哪个 Agent，并把每一步的输入、输出、事件和 checkpoint 都结构化落库。

## 项目映射
- 应用开发智能体：Router → Planner → Codegen → QA → Deploy，拆成 10+ 个 Agent 角色
- 运维智能体：Triage → Evidence → Diagnosis → Approval → Execution → RCA，拆成 10+ 个 Agent 角色
- 两个项目都不是"让大模型互相对话"，而是结构化任务编排

## 高频追问
1. 为什么不在一个大 Prompt 里完成所有事？
2. 多 Agent 不会更慢吗？
3. 你怎么决定拆成几个 Agent？

## 我的回答要点
> 我拆 Agent 的标准不是越多越好，而是看一个环节有没有独立职责、独产产物、独立验证标准和独立失败恢复需求。如果一个大模型能在一个 Prompt 里完成且输出可控，我不会拆；但如果涉及多步副作用（建表、写文件、部署），或需要人工审批、风险审查，我一定会拆成独立 Agent，每个 Agent 的输出是结构化 JSON，方便分步验证、错误定位和断点恢复。
