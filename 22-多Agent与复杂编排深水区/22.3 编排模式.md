# 22.3 编排模式

> 所属分支：[[22-多Agent与复杂编排深水区/_index|22-多Agent与复杂编排深水区]]

## 子节点 / 待填充要点
- 任务依赖图 vs 链式调用 vs 随机对话
- 并行 vs 串行执行
- 状态机设计
- 应用开发 Agent 的编排结构
- 运维 Agent 的编排结构

## 一句话定义
多 Agent 编排不是简单链式调用，而是"任务依赖图 + 状态机"：任务依赖图负责描述节点之间的前后依赖和并行关系，状态机负责记录每个节点的当前状态。

## 解决什么问题
链式调用无法表达并行关系，随机对话不可控。任务依赖图 + 状态机既能表达复杂依赖关系（并行、串行、条件分支），又能让每一步状态可追踪、可恢复。

## 编排模式对比

| 模式 | 适用场景 | 优点 | 缺点 |
|------|---------|------|------|
| 链式调用（Pipeline） | 步骤严格有序 | 简单易懂 | 无法并行，中间失败全链路重来 |
| 任务依赖图 + 状态机 | 有并行/条件/审批的复杂流程 | 灵活、可恢复、可审计 | 实现复杂度较高 |
| 多 Agent 对话（AutoGen 风格） | 开放讨论、创意生成 | 灵活 | 不可控、状态难以追踪 |
| Supervisor-Worker | 固定工作流 | 清晰的分层 | 单点故障 |

本项目的选择：**任务依赖图 + 状态机**，适合面试表达且技术可落地。

## 编排关键原则

1. **并行优先**：无依赖关系的节点（如 UI 规划、Schema 规划、路由规划）应并行执行
2. **副作用串行**：有副作用的节点（建表、文件写入、部署、审批、执行）必须串行，且前后打 checkpoint
3. **人工审批是强制同步点**：运维场景必须在高风险节点前暂停等人工
4. **Orchestrator 不负责智能判断**：它只管"任务流转"，不管"怎么做"

## 状态机设计

每个 Agent 节点的状态流转：
```text
PENDING → RUNNING → SUCCESS / FAILED / WAITING_APPROVAL
                                 ↓
                             RETRY → SUCCESS / FAILED
```

| 状态 | 含义 |
|------|------|
| PENDING | 等待前置节点完成 |
| RUNNING | 正在执行 |
| SUCCESS | 执行成功，可流转下一节点 |
| FAILED | 执行失败，可重试或终止 |
| WAITING_APPROVAL | 等待人工审批 |
| RETRY | 失败后重试中 |

## 项目映射
- 应用生成平台：Router → Planner（并行）→ Codegen → QA → Deploy（串行）
- OpsPilot：Triage → Evidence（并行）→ Diagnosis → Approval（同步点）→ Execute → Verify → RCA（串行）

## 高频追问
1. 为什么不用 LangGraph/AutoGen 的多 Agent 对话模式？
2. 并行节点怎么保证数据一致性？
3. 节点失败后怎么恢复？怎么防止重复执行？

## 我的回答要点
> 我的 Agent 编排不是简单链式调用，而是"任务依赖图 + 状态机"。任务依赖图负责描述节点之间的前后依赖和并行关系，状态机负责记录每个节点当前处于等待、执行、成功、失败、等待审批还是已完成。Orchestrator 根据当前状态和依赖关系，决定下一步调哪个 Agent，并把每一步的输入、输出、事件和 checkpoint 都结构化落库。
