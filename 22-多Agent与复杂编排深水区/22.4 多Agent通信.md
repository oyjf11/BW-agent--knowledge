# 22.4 多Agent通信

> 所属分支：[[22-多Agent与复杂编排深水区/_index|22-多Agent与复杂编排深水区]]

## 子节点 / 待填充要点
- Agent 不直接共享内存
- 通过数据库结构化中间产物协作
- JSON Schema 约束输入输出
- 应用开发 Agent 通信示例
- 运维 Agent 通信示例

## 一句话定义
Agent 之间不直接共享内存或互相调用，而是通过数据库里的结构化中间产物协作，每个 Agent 从数据库读取上游 Agent 的输出，处理后写回数据库。

## 解决什么问题
Agent 之间直接互相调用会导致：
- 状态不可追踪（谁传了什么数据给谁）
- 失败后无法恢复（中间数据丢失）
- 无法并行（必须等待上一个完成才能开始）
- 难以审计和回放

## 通信机制

### 核心原则
```
Agent A → 处理 → 结构化输出 → 写入 DB
                                 ↓
Agent B → 从 DB 读取输入 → 处理 → 结构化输出 → 写入 DB
                                 ↓
Agent C → 从 DB 读取输入 → ...
```

### 各 Agent 之间的数据传递

#### 应用开发智能体
| 上游 Agent | 输出（存入 DB） | 下游 Agent | 读取字段 |
|-----------|---------------|-----------|---------|
| Router | intent JSON | Context Agent | intent_type, targets |
| Context Agent | project_context | UI/DB/Routing Planner | pages, schemas, routes |
| UI Planner | page_change_plan | Codegen | target_files, component_plan |
| DBA Planner | table_plan, migration_plan | SQL Agent | fields, types, indexes |
| Codegen | file patches | QA Agent | changed_files, patch_url |
| QA Agent | verification_result | Deploy Agent | passed, errors |

#### 运维智能体
| 上游 Agent | 输出（存入 DB） | 下游 Agent | 读取字段 |
|-----------|---------------|-----------|---------|
| Ticket Intake | normalized_ticket | Triage Agent | service, description |
| Triage Agent | severity, incident_type | Evidence Planner | service, fault_type |
| Evidence Planner | evidence_plan | Evidence Collectors | sources, queries |
| Evidence Collectors | evidence_items | Diagnosis Agent | evidence_list, raw_refs |
| Diagnosis Agent | root_cause, confidence | Critic Agent | hypotheses, evidence_chain |
| Remediation Planner | remediation_plan | Approval Agent | actions, risk_level, rollback |

### JSON Schema 约束
每个 Agent 的输入/输出都用 JSON Schema 约束，保证下游能可靠解析：

```json
{
  "router_output": {
    "intent": "add_page | modify_page | modify_schema | modify_route",
    "confidence": 0.95,
    "targets": ["customer-list"],
    "tasks": ["create_page", "add_route"]
  }
}
```

```json
{
  "evidence_item": {
    "source_type": "k8s | mysql | alb | oss",
    "source_name": "prod-cluster",
    "query": "...",
    "result_summary": "3 个 pod 中 2 个 CrashLoopBackOff",
    "raw_result_ref": "oss://agent-runs/run_123/evidence/k8s_pods.json",
    "confidence": 0.92
  }
}
```

## 项目映射
- 应用生成平台：Agent 之间通过 agent_steps 表和 agent_artifacts 表传递结构化中间产物
- OpsPilot：Agent 之间通过 evidence_items、diagnosis_results、remediation_plans 等表传递

## 高频追问
1. Agent 间为什么不直接调 API，要通过数据库？
2. 大 JSON 产物（代码、日志）怎么传？塞数据库吗？
3. 下游 Agent 怎么知道上游的产物已经准备好了？

## 我的回答要点
> Agent 之间不直接共享内存，也不通过函数调用传递数据，而是通过数据库里的结构化中间产物协作。上游 Agent 完成后，把结构化 JSON 写入对应的表（agent_steps、agent_artifacts、evidence_items 等），下游 Agent 通过 run_id + step_id 读取。这样做的好处是每一步都可追踪、可审计、可回放，节点失败后可以从最近的 checkpoint 恢复，不需要重跑来时的所有节点。
