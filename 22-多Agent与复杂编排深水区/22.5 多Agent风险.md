# 22.5 多Agent风险

> 所属分支：[[22-多Agent与复杂编排深水区/_index|22-多Agent与复杂编排深水区]]

## 子节点 / 待填充要点
- 多 Agent 的核心风险
- 副作用节点的幂等控制
- 错误传播与隔离
- 成本与延迟
- 运维特有的安全风险

## 一句话定义
多 Agent 系统的风险不在于 Agent 数量多，而在于副作用节点（建表、写文件、部署、执行写操作）的不可逆和人工审批节点的长时间等待。

## 核心风险

| 风险 | 说明 | 缓解措施 |
|------|------|---------|
| 副作用重复执行 | 建表、文件写入、部署、SQL 执行失败后重试会导致重复操作 | 每个副作用节点前后打 checkpoint + 幂等 key |
| 人工审批超时 | 审批可能隔很久，Worker 可能中途重启 | WAITING_APPROVAL 状态持久化，审批后从 checkpoint 恢复 |
| 错误传播 | 上游 Agent 的输出错误导致下游连锁错误 | JSON Schema 校验 + QA/Critic Agent 验证 + 节点输出不和下游紧耦合 |
| 并行结果不一致 | 多个并行节点产出的结果冲突 | 并行节点产出后统一汇总再进入串行环节 |
| 成本膨胀 | Agent 数量多，模型调用次数多 | Router 前置过滤不需要全链路，缓存 RAG 检索结果 |
| 延迟增加 | 串行节点逐级等待 | 无依赖节点并行执行，减少串行链路长度 |
| 生产过程安全 | 运维 Agent 误操作生产系统 | 只读优先 → 人工审批 → 模拟执行 → 受控执行 → 回滚 |

## 副作用节点控制

副作用节点（产生不可逆操作的节点）的核心控制策略：

```text
执行前：
  - 检查 idempotency_key 是否已存在 → 如果存在，跳过执行
  - 保存 input_hash 到 checkpoint
  - 保存状态为 RUNNING

执行后：
  - 保存 output_hash 到 checkpoint
  - 保存状态为 SUCCESS
  - 保存 artifact_refs

恢复时：
  - 如果 checkpoint 状态为 SUCCESS 且 output_hash 匹配 → 跳过
  - 如果 checkpoint 状态为 RUNNING 且超时 → 检查实际是否已执行，决定重试或跳过
  - 如果 checkpoint 状态为 FAILED 且 retry_count < max_retry → 重试
```

## 应用生成场景的特殊风险

### 关键 checkpoint 节点（完整列表）

应用开发智能体的 checkpoint 围绕代码、Schema、SQL、版本设计：

| 节点 | checkpoint 内容 |
|---|---|
| `REQUEST_RECEIVED` | 用户原始需求、app_id、tenant_id |
| `ROUTER_DONE` | intent、任务类型、置信度 |
| `CONTEXT_READY` | 检索到的页面、Schema、路由、历史版本 |
| `UI_PLAN_DONE` | 页面变更计划 |
| `DB_PLAN_DONE` | 表结构变更计划 |
| `ROUTING_PLAN_DONE` | 路由变更计划 |
| `CODEGEN_DONE` | 生成的文件 patch、文件 hash |
| `SQL_GENERATED` | SQL 脚本、migration_id |
| `MIGRATION_APPLIED` | SQL 执行结果 |
| `PREVIEW_READY` | Sandpack 预览结果 |
| `QA_PASSED` | lint / tsc / runtime 结果 |
| `VERSION_SAVED` | app_version_id |
| `DEPLOYED` | 部署地址 |

### CODEGEN_DONE checkpoint 示例

```json
{
  "run_id": "run_app_001",
  "node_key": "CODEGEN_DONE",
  "status": "SUCCESS",
  "state_json": {
    "app_id": "app_123",
    "version_id": "ver_008",
    "target_files": ["src/pages/CustomerList.tsx", "src/routes.tsx"],
    "changed_pages": ["customer-list"],
    "changed_schema": ["customers"]
  },
  "artifact_refs": {
    "patch": "oss://agent-runs/run_app_001/patch.diff",
    "files_snapshot": "oss://apps/app_123/ver_008/files.json"
  },
  "input_hash": "hash_user_request_context",
  "output_hash": "hash_generated_patch"
}
```

### 恢复逻辑示例

SQL 已经建表成功，但预览失败：
```text
SQL_GENERATED ✅
MIGRATION_APPLIED ✅
PREVIEW_READY ❌
```
系统恢复时不应该重新建表，而是读取最近成功 checkpoint → 发现 migration 已 applied → 从 PREVIEW_READY 重新开始 → 把 Sandpack 错误交给 QA / Patch Agent 修复。

### 三种特殊风险

- **SQL 脚本重复执行**：建表脚本已成功但预览失败 → 恢复时不重新建表，从预览步骤开始
- **文件覆盖冲突**：两个生成任务同时修改同一文件 → 通过 `lock:app:{app_id}` 分布式锁防止
- **Schema 破坏性变更**：字段删除、类型变更 → 人工确认后才能执行

## 运维场景的特殊风险

运维智能体的 checkpoint 更关键，涉及生产安全。

### 关键 checkpoint 节点（完整列表）

| 节点 | checkpoint 内容 |
|---|---|
| `TICKET_RECEIVED` | 工单原文、告警、服务名 |
| `TRIAGE_DONE` | 服务、等级、故障类型 |
| `EVIDENCE_PLAN_DONE` | 要采集哪些证据 |
| `EVIDENCE_COLLECTED` | 证据列表、证据来源 |
| `DIAGNOSIS_DONE` | 根因假设、置信度 |
| `RISK_REVIEW_DONE` | 风险等级、缺失证据 |
| `REMEDIATION_PLAN_DONE` | 修复方案、回滚方案 |
| `WAITING_APPROVAL` | 等待谁审批、审批内容 |
| `APPROVED` | 审批人、审批结果 |
| `MOCK_EXECUTED` | 模拟执行结果 |
| `EXECUTED` | 实际执行结果 |
| `VERIFIED` | 指标是否恢复 |
| `RCA_GENERATED` | RCA 报告 |

### WAITING_APPROVAL checkpoint 示例

```json
{
  "run_id": "run_ops_001",
  "node_key": "WAITING_APPROVAL",
  "status": "WAITING_APPROVAL",
  "state_json": {
    "ticket_id": "ticket_9527",
    "service": "order-service",
    "severity": "P1",
    "root_cause": "order-service pod CrashLoopBackOff caused by config error",
    "confidence": 0.87,
    "risk_level": "HIGH",
    "remediation_action": "rollback deployment to previous stable version",
    "rollback_plan": "restore deployment image tag v1.2.7"
  },
  "artifact_refs": {
    "evidence": "oss://agent-runs/run_ops_001/evidence.json",
    "remediation_plan": "oss://agent-runs/run_ops_001/remediation.md"
  },
  "idempotency_key": "ticket_9527:rollback:v1.2.7"
}
```

运维场景需要 **强制在高风险节点前打 checkpoint**：

```text
诊断完成 → 生成修复方案 → [checkpoint: WAITING_APPROVAL]
  → 人工审批 → [checkpoint: APPROVED]
  → 模拟执行 → [checkpoint: MOCK_EXECUTED]
  → 真实执行 → [checkpoint: EXECUTED]
  → 验证
```

原因：
- 人工审批可能隔很久才发生，Worker 重启不能丢状态
- 执行动作不能重复触发（如重复重启服务、重复回滚）
- 出问题后要能审计是谁批准、执行了什么、结果如何

## 项目映射
- 应用生成平台：动态建表 9 项风险控制、Schema diff 增量迁移、lock 防并发修改
- OpsPilot：只读优先、人工审批卡点、模拟执行、执行幂等控制、完整审计链路

## 高频追问
1. 多个 Agent 并行执行时，如果一个失败了，其他怎么办？
2. 怎么防止同一个副作用被执行两次？
3. 运维 Agent 的安全风险怎么控制？

## 我的回答要点
> 多 Agent 系统的风险控制核心是：副作用节点前后打 checkpoint、每个有副作用的操作带幂等 key、人工审批节点状态持久化防止 Worker 重启丢状态。应用生成里重点防止 SQL、文件写入、部署这类副作用重复执行；运维智能体里重点是审批、执行、验证前后打 checkpoint，确保流程可恢复、可审计、可回放。
