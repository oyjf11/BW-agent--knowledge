# 23.4 质量门禁

> 所属分支：[[23-AI Coding工程化深水区✅/_index|23-AI Coding工程化深水区]]

## 子节点 / 待填充要点
- SDD / Spec Driven Development
- Lint → TypeScript → Test → Build 验证链路
- Playwright 测试与失败归因
- TDD / BDD 在 AI Coding 中的应用

## 一句话定义
质量门禁是 AI 生成代码进入主干前的强制校验层，包括 Spec 对齐、静态检查、类型检查、单元测试、E2E 测试、构建验证和代码审查。

## 解决什么问题
AI 生成代码不能靠肉眼看。需要通过可执行的标准（lint→tsc→test→build→review）串联成一道硬门禁。

## 如何实现

### 验证链路
```text
Spec 定义验收标准
  ↓
代码生成
  ↓
静态检查：ESLint / Prettier
  ↓
类型检查：TypeScript
  ↓
单元测试：Vitest
  ↓
E2E：Playwright
  ↓
构建验证：npm run build
  ↓
代码审查：规则 + AI Review
  ↓
生成自测报告
```

### Playwright 测试失败归因
| 证据 | 可能原因 |
|------|----------|
| 页面白屏 | 代码运行错误 |
| console error | JS 异常 |
| network 404/500 | 接口或 mock 问题 |
| selector 找不到 | 页面没渲染或选择器错 |
| 截图正常但断言失败 | 断言文案或业务预期错 |
| 点击无效 | 遮罩、disabled、异步状态 |
| 超时 | 时序问题、接口慢、等待条件错误 |

### TDD 实践
```text
先根据 Spec 生成测试 → 测试审核 → AI 生成实现 → 运行测试 → 失败修复
```

### BDD 实践
> Given 当前用户已登录，When 点击导出按钮，Then 应生成导出任务并展示成功提示。

## 项目映射
- 应用生成平台：QA 阶段执行 lint → tsc → build → Sandpack 运行验证
- AI Coding 工具包：Runner 收集错误日志、截图、trace 作为修复依据

## 高频追问
1. AI 生成代码后怎么验证？
2. Playwright 测试失败，怎么判断是代码错还是用例错？
3. TDD / BDD 在 AI Coding 中怎么做？

## 我的回答要点
> AI 生成代码不能靠肉眼看。最基本要经过 lint、类型检查、测试和构建。对于前端页面，Playwright 很关键，因为它能验证真实交互路径。执行失败后，Runner 会收集错误日志、截图、trace、console 和 network，作为下一轮修复依据。我不会直接把测试失败归因给代码，会结合多个证据链判断是代码问题还是用例问题。
