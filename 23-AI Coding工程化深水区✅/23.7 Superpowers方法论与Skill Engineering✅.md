# 23.7 Superpowers方法论与Skill Engineering

> 所属分支：[[23-AI Coding工程化深水区✅/_index|23-AI Coding工程化深水区]]

## 子节点 / 待填充要点
- Superpowers 是什么

## 一句话定义

Superpowers（`obra/superpowers`）是一套 Agent Skills 框架 + 软件开发方法论，不是让模型变聪明，而是通过可组合 skills、强制工程流程、TDD 验证、Subagent 分工和工作区隔离，把 AI Coding 从"每次靠模型临场发挥"推进到"可复用、可约束、可组合的方法论系统"。

## 解决什么问题

AI Coding 的真实痛点不是模型能力不够，而是执行不稳定：
- 有时不先理解需求直接改代码
- 有时不写测试直接实现
- 复杂任务没有计划、拆解和审查
- 不同 session、不同开发者执行风格不一致
- 长任务中容易上下文漂移

Superpowers 把这些不稳定行为变成一套默认流程。

## 如何实现

### 1. 核心工作流

```text
需求沟通 → 提炼 spec → 分块展示给用户确认
  → 生成实现计划 → 等用户确认 go
  → 子 agent 分任务执行 → 每个任务实现后 review
  → TDD 红绿循环 → 最后选择 PR / merge / stop
```

### 2. Skill 自动触发机制

通过 session hook / bootstrap prompt 告诉 agent：
1. 你有 skills
2. 你要搜索 skills
3. 如果有适用 skill，必须使用它

**不是让用户记住流程，而是让 agent 自己记住流程。** 这降低了使用成本，解决了"每次都要提醒模型遵守规范"的问题。

### 3. Meta-skill：先学会"如何使用技能"

Superpowers 最先进的设计是 meta-skill 机制：

```text
当你开始任务时，先判断有没有适合的 skill
→ 如果有，必须读取并使用
→ 如果没有，可以创建或改进 skill
```

这等价于：

```text
Router → Skill Selection → Agent Execution
```

是一个 skill 选择路由器，降低了随机性。

### 4. Brainstorm → Plan → Implement 强制工程节奏

不是"直接代码生成器"，而是强制分阶段：

```text
Brainstorm：澄清目标、理解需求
Plan：形成可执行计划
Implement：按计划执行
Review：检查实现质量
Test：TDD / 回归验证
```

防止 AI Coding 里最常见的坏路径：用户一句话需求 → AI 直接全量改代码 → 跑不起来 → 越修越乱。

### 5. Worktree 并行隔离

在 git repo 中自动创建 worktree，让并行任务互不污染：

```text
main branch
├── worktree/task-a
├── worktree/task-b
└── worktree/task-c
```

好处：每个 agent 有独立工作区、方便并发、方便回滚、方便 review、避免多 agent 改同一份 working directory。

### 6. Subagent-driven Development

不只是一个 agent 从头做到尾，而是：

```text
主 agent：负责规划、调度、验收
子 agent：负责具体任务实现
review agent：负责检查实现质量
```

对应真实团队：PM / Tech Lead / Engineer / Reviewer。

### 7. 真正的 RED/GREEN TDD

先定义失败用例 → 再实现最小代码 → 再让测试变绿。

不是"代码写完再补一个能过的测试"，而是让任务有一个外部判定标准：**不是 AI 说完成，而是测试通过才算完成。**

### 8. Self-improving Skills

Skills 可被新增、修改、组合，沉淀新的工作流：

```text
Bad Case → 归因 → 规则/Skill/Planner Prompt 更新 → 下一次复用
```

## 设计哲学

### 哲学一：不是提升模型智商，而是提升执行纪律

```
LLM 已经足够聪明，但缺少纪律。
```

Superpowers 不做更复杂的模型推理，而是做：流程约束、skill 选择、计划先行、测试驱动、子任务隔离、审查闭环、可复用工程方法。

> **Agent 产品化，不是让模型更聪明，而是让模型少犯工程错误。**

### 哲学二：从 Prompt Engineering 转向 Skill Engineering

| 阶段 | 特征 | 问题 |
|------|------|------|
| Prompt | 一次性提示 | 难复用，难维护 |
| AGENTS.md / CLAUDE.md | 项目级规则 | 偏静态，容易膨胀 |
| Skills | 任务级方法论 | 可选择、可组合 |
| Subagents | 角色级执行单元 | 可分工、可并行 |
| Workflow Runtime | 状态机执行 | 可恢复、可审计 |

Superpowers 处在 **Skills + Subagents + Workflow Discipline** 这一层。

### 哲学三：把 AI 当"初级工程师团队"，不是"万能大神"

```
不要假设 agent 天然可靠。
要把它当成需要明确任务书、边界、测试和 review 的执行者。
```

AI Coding 最危险的心智模型是"AI 是大神，我一句话它就该全懂"。更合理的心智模型是：**AI 是高执行力但低稳定性的 junior engineer，你需要给它 spec、plan、tests、review gate。**

### 哲学四：从"聊天式 AI"变成"流程化 Agent"

普通 Claude Code / Cursor / OpenCode：
```text
用户输入 → 模型响应 → 工具调用 → 继续响应
```

Superpowers 试图变成：
```text
任务进入 → 选择 skill → 生成 spec → 用户确认
  → 生成 plan → 用户确认 → 创建隔离工作区
  → 分配 subagent → TDD 实现 → review → PR / merge
```

从 **chat interface** 到 **agent workflow** 的转变。

## 六大先进关键词

| 关键词 | 含义 | 解决的问题 |
|--------|------|-----------|
| **Skill-first** | 不是"模型先想"，而是"先找已有技能" | 降低随机性 |
| **Spec-first** | 不是直接写代码，而是先把目标结构化 | 降低误解需求概率 |
| **Plan-first** | 不是边写边想，而是先拆任务、定顺序、识别边界 | 降低长任务失控概率 |
| **Test-first** | 不是写完自夸完成，而是用测试定义完成标准 | 降低幻觉交付概率 |
| **Worktree isolation** | 不是所有任务污染主目录，而是隔离执行、方便并发和回滚 | 提高工程安全性 |
| **Self-improving skills** | 不是一次性 prompt，而是把新经验沉淀成 skill | 形成能力复利 |

## 局限性（面试中展示批判性思维）

### 局限一：仍依赖模型遵守自然语言规则

Skills 本质还是 Markdown / prompt 规则，不是强制状态机。如果模型不遵守，仍然可能跳步。企业级场景需要叠加：

```text
状态机 + JSON Schema + 工具权限 + 测试门禁 + 执行日志 + 人工审批 + CI 校验
```

### 局限二：Skill 越多，选择和治理越难

- 什么时候触发哪个 skill？
- 多个 skill 冲突怎么办？
- skill 版本如何管理？
- 恶意 skill 如何防？
- skill 质量如何评估？

近期研究指出 SKILL.md 这类自然语言技能注册机制存在语义供应链风险（arXiv 2605.11418）：skill 描述影响 agent 的发现、选择和信任过程。

### 局限三：企业级需要更完整的治理体系

企业内部开发套件不能只讲"我们有很多 skills"，还要讲：

```text
Skill 准入 → Skill 版本管理 → Skill 权限边界
  → Skill 执行日志 → Skill 效果评估 → Skill 下线机制
```

## 项目映射

### 对 AI Coding 工程化体系的启发

可以将开发套件表述为：

> 我们不是简单封装一个 AI 编码工具，而是参考 Superpowers 这类 Skills-based Agent Framework 的思想，把研发流程拆成可复用的 Commands、Agents、Skills 和 Rules。

| Superpowers | 我们的开发套件 |
|-------------|---------------|
| 偏通用 coding workflow | 偏企业内部研发流程 |
| 面向 Claude Code / Codex / OpenCode 等工具 | 面向公司内部 OpenCode / 工程规范 / CI/CD |
| 核心是 skills 方法论 | 核心是需求、开发、测试、MR、CI/CD 全流程 |
| 强调 TDD、worktree、subagent | 强调 Spec、Runner、Playwright、质量门禁、Bad Case 数据闭环 |

### 对应用生成智能体的启发

- **引入 Skill Registry**：`add_page_skill`、`modify_form_skill`、`debug_sandpack_skill` 等
- **引入强制 Plan Gate**：复杂需求不能直接生成代码
- **引入 Worktree / Version Sandbox**：每次生成有隔离版本
- **引入 QA Skill**：每种错误有固定排查流程

### 对运维智能体的启发

运维智能体的 skill 思路：

```text
k8s_pod_crashloop_skill
mysql_slow_query_skill
alb_5xx_skill
deployment_rollback_skill
```

每个 skill 是一套标准排查 SOP：触发条件 → 收集证据 → 禁止的高风险动作 → 判断根因 → 输出建议 → 验证修复。

## 高频追问

1. **Superpowers 和 LangChain/LangGraph 有什么区别？**
   → Superpowers 偏 coding methodology，LangChain 偏 LLM 应用框架。前者解决 "AI 怎么写代码" 的流程问题，后者解决 "怎么调用 LLM" 的技术问题。

2. **Skills 和 AGENTS.md 有什么区别？**
   → AGENTS.md 是项目级静态规则，skills 是任务级可组合方法论。Skills 可选择、可组合、可自我改进。

3. **你们自己的平台比 Superpowers 强在哪里？**
   → Superpowers 偏个人开发者 workflow，我们偏企业内部落地：有状态机、JSON Schema、工具权限、CI 门禁、Bad Case 闭环和团队级治理。

## 我的回答要点

面试时可以先讲 Superpowers 的分析（展示行业视野），再衔接自己的项目：

> Superpowers 受欢迎的本质，不是它给模型增加了什么魔法能力，而是它把 AI Coding 从一次性 prompt 推进到了 Skills-based Workflow。它通过 session 启动注入、skill 自动检索、brainstorm-plan-implement 流程、TDD、subagent 执行、worktree 隔离和 review gate，让 AI 不再每次临场发挥，而是按稳定的软件工程方法做事。

衔接项目：

> 我自己的 AI 开发套件也是类似思路，但更偏企业内部落地。我不会只把 AI 当代码生成器，而是把研发流程拆成 Commands、Agents、Skills 和 Rules，围绕需求解析、任务拆解、代码生成、测试验证、代码审查、MR 和 Bad Case 反馈形成闭环。这样做的目标是让 AI Coding 从个人提效工具变成团队可复用、可验证、可治理的工程体系。

**最终结论**：Superpowers 的核心先进性 = Skills 工程化 + 流程纪律 + TDD 验证 + Subagent 分工 + 工作区隔离 + 经验可沉淀。它火的原因也很直接——模型能力已经足够强，但真实工程需要的是稳定、可控、可复用、可验证，Superpowers 正好补上了这层工程方法论。
