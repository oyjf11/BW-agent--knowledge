# 24.2 Router深水区

> 所属分支：[[24-AI应用生成平台深水区✅/_index|24-AI应用生成平台深水区]]

## 子节点 / 待填充要点
- 三层路由设计
- 意图分类（新建、修改页面、加字段、加路由、修 bug）
- target_files 定位
- 结构化 intent JSON 输出

## 一句话定义
Router 是生成流水线的第一道关卡，负责判断用户输入的意图类型，不读取全量源码，只基于轻量元信息输出结构化任务描述。

## 解决什么问题
避免模型每次全量重写项目。通过先判断"这是什么任务"再分发给对应 Planner，缩小每次生成的上下文范围，提高可控性。

## 如何实现
```text
第一层：quick rules
  - 关键词、正则、页面名、字段名、路径匹配

第二层：场景化检索
  - 从历史任务样例、意图样例、平台规则中找相似案例

第三层：模型兜底
  - 输出结构化 intent JSON
```

输出示例：
```json
{
  "intent": "modify_app",
  "tasks": ["ui_change", "schema_change", "routing_change"],
  "targets": {
    "pages": ["customer-list"],
    "tables": ["customers"]
  },
  "confidence": 0.86
}
```

## 项目映射
- Router 阶段只需要用户需求、轻量页面元信息、路由信息和少量历史样例
- 规则 → 检索 → 模型三级兜底

## 高频追问
1. Router 和 Planner 的区别是什么？
2. Router 为什么不读全量源码？
3. confidence 低于阈值怎么处理？

## 我的回答要点
> Router 解决方向问题，Planner 解决路径问题。Router 判断"这是什么任务"，Planner 判断"这个任务具体怎么做"。Router 不应该读取全量源码，它只需要用户需求、轻量页面元信息、路由信息和少量历史样例。先用规则覆盖高确定性场景，再用相似案例检索增强，最后才用模型兜底输出结构化 intent。
