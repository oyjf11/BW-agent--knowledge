# 24.5 企业级能力

> 所属分支：[[24-AI应用生成平台深水区✅/_index|24-AI应用生成平台深水区]]

## 子节点 / 待填充要点
- 与 LlamaCoder 原版的 8 项差异
- MySQL 控制面 vs PG/Supabase 数据面
- 企业 SSO + Supabase RLS 多租户隔离
- 动态建表安全控制
- Schema diff 增量迁移
- 版本管理、审计日志、Bad Case

## 一句话定义
在原版 LlamaCoder 的 prompt-to-app 能力之上，补齐企业级所需的数据分层、权限体系、多租户隔离、动态建表安全、增量迁移、版本管理和审计能力。

## 解决什么问题
原版 LlamaCoder 是 Demo 工具，缺少企业级数据层、权限层、版本层和交付层。企业化改造使它能作为内部轻应用生成平台落地。

## 如何实现

### LlamaCoder vs 二次改造对比
| 原版 LlamaCoder | 二次改造后 |
|---------------|-----------|
| 一句 prompt 生成小应用 | 面向企业内部轻应用生成 |
| 偏 Demo / Claude Artifacts | 偏企业级平台 |
| 主要生成 React 前端代码 | 生成页面、Schema、SQL、CRUD、路由 |
| Together AI 直接生成代码 | Router / Planner / Codegen 多阶段控制 |
| 数据层较弱 | MySQL 控制面 + PG/Supabase 数据面 |
| 无企业权限体系 | 企业 SSO + Supabase JWT + RLS |
| 单次生成为主 | 支持对话式增量修改 |
| 简单预览 | Sandpack 预览 + 错误反馈 + 长代码优化 |
| 缺少平台元数据 | 应用、页面、版本、任务状态、审计落 MySQL |

### 动态建表安全
| 风险 | 控制方式 |
|------|----------|
| SQL 注入 | 不直接拼用户输入，Schema 白名单生成 |
| 表名混乱 | 统一命名规则 |
| 字段类型错误 | 类型枚举限制 |
| 缺少 tenant_id | 建表模板强制注入 |
| 缺少 RLS | 建表后强制启用 RLS |
| 重复建表 | MySQL 记录 schema_version |
| 破坏旧数据 | 迁移前 diff 和备份 |
| SQL 执行失败 | dry-run / transaction / rollback |
| 字段删除风险 | 默认禁止自动删除字段 |

### Schema 增量迁移
```text
旧 Schema → 新需求生成候选 Schema → Schema diff
  ├─ 新增字段 / 新增表 → 低风险自动执行
  └─ 字段删除 / 类型变更 / 关系变更 → 人工确认
→ 更新 MySQL Schema 版本 → 前端基于新 Schema 更新表单
```

## 项目映射
- 平台控制面：MySQL（apps、app_pages、app_versions、agent_runs、agent_steps、generation_artifacts、project_snapshots、tenant_app_bindings、audit_logs、prompt_versions、bad_cases）
- 用户数据面：PostgreSQL / Supabase（业务表带 tenant_id、created_by、updated_by）

## 高频追问
1. 你们和原版 LlamaCoder 的区别是什么？
2. 为什么选 LlamaCoder 和 Together AI SDK？
3. 动态建表有什么风险？怎么控制？
4. 新旧 Schema 怎么做增量修改？

## 我的回答要点
> 原版 LlamaCoder 更像验证"自然语言生成 React 应用"的交互闭环。我们真正做的是把它企业化：把一次性代码生成拆成多阶段控制，补齐数据层 MySQL + PG/Supabase、权限层 SSO + RLS、版本层和交付层。动态建表的核心风险是模型输出不可控，所以我们不让模型自由写 SQL，而是先约束成 Schema，再由平台模板生成 SQL。所有业务表强制带 tenant_id，建表后自动开启 RLS。
