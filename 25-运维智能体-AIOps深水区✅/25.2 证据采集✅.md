# 25.2 证据采集

> 所属分支：[[25-运维智能体-AIOps深水区✅/_index|25-运维智能体-AIOps深水区]]

## 子节点 / 待填充要点
- 多源证据采集架构
- Evidence Planner 职责
- Evidence Collector Agents（MySQL、K8s、ALB、OSS）
- 并发采集与结果汇总
- evidence_items 数据结构

## 一句话定义
运维智能体通过 Evidence Planner 制定采集计划，再由多个 Evidence Collector Agent 并发接入 MySQL、K8s、ALB、OSS 等多源只读数据，将采集到的证据结构化存入 evidence_items 表。

## 解决什么问题
故障定位需要跨多个数据源串联证据（服务状态、资源信息、异常记录、告警上下文、历史工单），单一数据源无法形成完整证据链。

## 如何实现

### 证据采集流程

```text
Triage Agent 完成分诊（service、severity、incident_type）
   ↓
Evidence Planner 生成采集计划
   ↓
┌────────────┬────────────┬────────────┬────────────┐
│ MySQL Agent │ K8s Agent  │ ALB Agent  │ OSS Agent  │  ← 并发采集
└─────┬──────┴──────┬─────┴──────┬─────┴──────┬─────┘
      ↓             ↓            ↓            ↓
           Evidence Store（汇总）
                 ↓
          Diagnosis Agent 开始分析
```

### Evidence Planner 职责
先根据分诊结果判断要查哪些证据：
- P1 级故障：全量采集（MySQL + K8s + ALB + OSS + 日志）
- P3 级告警：针对性采集（只查相关服务的日志和指标）
- 已有类似工单：参考历史 RCA 中的证据采集路径

### Evidence Collector Agents

| Agent | 数据源 | 采集内容 | 权限 |
|-------|--------|---------|------|
| MySQL Agent | 业务数据库 | 慢 SQL、连接数、QPS、死锁 | 只读 |
| K8s Agent | 容器集群 | Pod 状态、事件、资源使用、日志 | 只读 |
| ALB Agent | 负载均衡 | 5xx 错误、延迟、连接数 | 只读 |
| OSS Agent | 对象存储 | 访问错误、延迟、配额 | 只读 |

### evidence_items 数据结构

```json
{
  "id": "ev_001",
  "run_id": "run_123",
  "ticket_id": "ticket_456",
  "source_type": "k8s",
  "source_name": "prod-cluster",
  "service": "order-service",
  "query": "kubectl get pods -n prod -l app=order-service",
  "result_summary": "3 个 pod 中 2 个 CrashLoopBackOff",
  "raw_result_ref": "oss://agent-runs/run_123/evidence/k8s_pods.json",
  "confidence": 0.92,
  "collected_at": "2026-06-01T10:20:00+08:00"
}
```

关键设计原则：
- 证据原文（大 JSON、截图、日志）不塞数据库，存 OSS/S3
- 数据库只存摘要、结构化字段和对象存储引用
- 每条证据带 `confidence` 字段，诊断时可用作权重
- 工具结果可缓存（Redis `tool_cache:{hash}`），避免短时间内重复采集

### EvidenceRecord 标准证据结构

所有工具返回应统一转成标准 EvidenceRecord，避免不同系统返回格式不一致导致诊断混乱：

```text
EvidenceRecord = {
  evidence_id       // 唯一证据 ID
  tool_name         // 来源工具名
  resource_type     // mysql / k8s / alb / oss
  resource_id       // 资源标识
  time_range        // 证据采集时间范围
  status            // normal / warning / critical / unknown
  finding           // 一句话关键发现
  key_metrics       // 关键指标摘要
  supports          // 支持哪些根因假设
  contradicts       // 反驳哪些根因假设
  confidence        // 证据置信度
  collected_at      // 采集时间
}
```

示例（MySQL 连接数异常）：

```json
{
  "evidence_id": "ev_mysql_001",
  "tool_name": "mysql.get_connection_stats",
  "resource_type": "mysql",
  "resource_id": "order_db",
  "status": "critical",
  "finding": "MySQL 当前连接数 198/200，接近上限",
  "supports": ["mysql_connection_exhausted"],
  "confidence": 0.91
}
```

示例（K8s Pod 正常——反证）：

```json
{
  "evidence_id": "ev_k8s_001",
  "tool_name": "k8s.get_pod_status",
  "resource_type": "k8s",
  "resource_id": "prod/order/order-service",
  "status": "normal",
  "finding": "Pod 无重启，无 OOMKilled",
  "contradicts": ["pod_crash", "oom_killed"],
  "confidence": 0.82
}
```

关键设计：每条证据不仅描述发现，还显式标注 `supports`（支持哪些根因）和 `contradicts`（反驳哪些根因），让 Diagnosis 节点能基于证据约束做诊断，而不是凭经验猜测。

### 范式升级：从纯工具并行到 Specialist Agent Pool（v2）

v1 架构中 evidence_fanout_node 仅将 plan 中的 task 通过 `asyncio.gather` 并行调用工具，返回 raw data 后由 aggregate 做简单规则评分。核心问题是：

- 每个工具调用是纯数据拉取，无推理分析能力
- 异常信号被淹没（几百条 K8s events 中 1 条 CrashLoopBackOff → aggregate 无法识别）
- 工具调用间无关联分析（K8s pod 重启时间与 DB 慢查询时间窗口的关系未被发现）

v2 升级为 **5 个独立 Specialist Agent 组成的分析池**：

```text
旧路径：planner → tool calls (asyncio.gather) → raw EvidenceItem → aggregate 规则评分

新路径：planner → AgentTask × 5 → SpecialistAgent.run() (ReAct) → SpecialistAnalysis → aggregate 关联图 + 因果链 + 矛盾检测
```

核心变化：让 Agent 在工具返回数据的那一刻就做一级分析，不把所有 raw data 堆给下游。不改变 StateGraph 拓扑（builder.py 零改动），通过 Feature Flag 双路径实现渐进式上线。

### SpecialistAgent 的双层推理架构

每个 SpecialistAgent 同时具备两类能力：

| 层级 | 机制 | 场景 | 输出 |
|------|------|------|------|
| **LLM 推理** | ReAct 循环（max 3 rounds）+ tool calling | LLM 可用 | 结构化 JSON 分析 |
| **规则兜底** | `_extract_signals_by_rules()` 硬编码规则 | LLM 超时/失败 | AnomalySignal 列表 |

规则兜底是确定性安全网：即使所有 LLM 调用都失败，K8s Agent 仍能通过检查 `containerStatuses.waiting.reason` 发现 CrashLoopBackOff，保证最坏情况下仍有可用的分析结论。

### 5 类 Agent 的确定性规则信号

| Agent | 规则 | 产出 |
|-------|------|------|
| K8s | `containerStatuses.waiting.reason` ∈ {CrashLoopBackOff, ErrImagePull, OOMKilled} → AnomalySignal | 确定性 pod 级健康信号 |
| DB | COMMAND≠'Sleep' 连接数 > 50 → warning；慢查询 > 10 → anomaly | 确定性 DB 瓶颈判断 |
| Log | 正则计数 ERROR\|FATAL\|Exception > 10 → warning | 确定性日志异常量信号 |
| Metrics | 相邻两点变化率 > 50% → anomaly | 确定性指标突变信号 |
| Deployment | 最近部署 < 2h → correlation_hint(target="k8s" or "logs", confidence=0.6) | 发布窗口关联 |

每条规则都是确定性的、可解释的，用于 LLM 不可用时的最低保障。

### Agent 级原子写入 + 失败回滚

fanout 中每个 Agent 的 evidence_items 写入采用 Agent 级原子写入：

```python
for result in results:
    agent_evidence = build_raw_evidence_items(result)
    try:
        state["evidence_items"].extend(agent_evidence)
        state["specialist_analyses"].append(result.model_dump())
    except Exception:
        # 回滚已写入的 evidence，保证 Agent 级原子性
        state["evidence_items"] = [e for e in state["evidence_items"] if e not in agent_evidence]
        state["specialist_analyses"].append(_build_degraded_shell(...))
```

Agent 间无依赖关系，单 Agent 原子性已满足，不需要全局事务。

### confidence LLM 自评不可靠

LLM 自评 confidence 通常偏高（0.8-0.95），但实际准确率仅 60-70%。代码层强制封顶 0.6，aggregate 中 `partial` 进一步降权 ×0.5。

## 项目映射
- OpsPilot v1：多源只读数据接入（MySQL、K8s、ALB/SLB、OSS），证据采集全部只读
- OpsPilot v2：Specialist Agent Pool（K8s、DB、Log、Metrics、Deployment 5 个 Agent），每个 Agent 自带 ReAct 循环 + 规则兜底
- 并发采集缩短证据收集时间
- EvidenceRecord 结构已定义，支撑诊断节点的证据驱动推理

## 高频追问
1. 怎么保证采集到的证据是可信的？
2. 证据来源太多怎么办？怎么控制采集范围？
3. 采集失败（比如 K8s API 超时）怎么处理？

## 我的回答要点
> 运维智能体的证据采集不是盲目全查，而是先由 Evidence Planner 根据故障类型和严重程度判断要查哪些数据源，再并发发起采集。MySQL Agent、K8s Agent、ALB Agent、OSS Agent 各自通过只读接口采集对应数据，采集结果结构化后统一汇总到 Evidence Store，带置信度和原始数据引用。数据库只存摘要和引用，大文件放对象存储。采集结果可以短期缓存在 Redis，避免短时间内重复查询生产集群。
