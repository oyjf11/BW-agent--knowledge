# 25.3 诊断逻辑

> 所属分支：[[25-运维智能体-AIOps深水区✅/_index|25-运维智能体-AIOps深水区]]

## 子节点 / 待填充要点
- Diagnosis Agent 根因假设生成
- Critic / Risk Agent 反向检查
- 证据链驱动 vs 规则驱动
- 置信度评估
- 缺失证据检测

## 一句话定义
诊断层由两个 Agent 配合完成：Diagnosis Agent 基于完整证据链生成根因假设，Critic / Risk Agent 从反面验证证据是否充分、评估操作风险。

## 解决什么问题
单模型直接给出诊断结论不可信，缺少反向验证和风险评估环节。双 Agent 设计让"提出假设"和"验证假设"分离，降低误判风险。

## 如何实现

### 诊断流程

```text
证据收集完成
   ↓
Diagnosis Agent：基于证据链 + 历史 RCA + SOP 生成根因假设
   ↓
输出：root_cause_hypotheses（按概率排序）
   ↓
Critic / Risk Agent：从反面检查
  - 证据是否充分？有没有缺失的关键证据？
  - 假设是否与已知事实矛盾？
  - 操作风险等级？
   ↓
输出：confidence、risk_level、missing_evidence
   ↓
Remediation Planner 基于确认后的根因生成处置方案
```

### Diagnosis Agent 的诊断维度

| 维度 | 说明 |
|------|------|
| 时间相关性 | 故障发生的时间点与变更、部署、告警的时间窗口重合度 |
| 空间相关性 | 受影响的服务、Pod、节点、数据库实例的拓扑关系 |
| 证据权重 | 每条证据的 confidence 加权，如 K8s CrashLoopBackOff 比 CPU 略高置信度更高 |
| 历史相似性 | 查询 historical_rcas 中是否有相似故障模式 |
| SOP 匹配 | 匹配 runbooks 中的已知故障模式 |

### Critic / Risk Agent 的反向检查

| 检查项 | 说明 |
|--------|------|
| 证据充分性 | 是否所有计划的证据都已采集成功？ |
| 假设排他性 | 是否存在其他能解释同一组证据的假设？ |
| 操作风险评估 | 如果按此诊断执行修复，最坏结果是什么？ |
| 缺失证据 | 哪些关键证据未采集到？是否需要补充采集？ |

### 诊断结果输出

```json
{
  "run_id": "run_ops_001",
  "service": "order-service",
  "root_cause_hypotheses": [
    {
      "hypothesis": "order-service pod CrashLoopBackOff caused by config error",
      "confidence": 0.87,
      "supporting_evidence": ["ev_001", "ev_003"],
      "contradicting_evidence": []
    },
    {
      "hypothesis": "order-service OOM caused by memory leak",
      "confidence": 0.12,
      "supporting_evidence": [],
      "contradicting_evidence": ["ev_002: memory usage normal"]
    }
  ],
  "risk_level": "HIGH",
  "missing_evidence": ["近期部署变更记录"],
  "recommended_actions": [
    "回滚 deployment 到上一个稳定版本"
  ]
}
```

### 诊断与处置的衔接

诊断完成后不直接执行，而是交给 Remediation Planner 生成处置方案：
- 如果 confidence >= 0.85 且 risk_level = LOW/MEDIUM：生成处置方案 + 模拟执行
- 如果 confidence < 0.85 或 risk_level = HIGH：标注风险，强制人工审批
- 如果有 missing_evidence：触发补充证据采集

### 跨 Agent 关联推理（v2 Specialist Agent Pool 新增能力）

v2 版本中 aggregate 从简单的"数 evidence 数量 + 关键词匹配"升级为三个维度的推理：

**1. 关联图（Correlation Graph）**

利用每个 SpecialistAnalysis 中的 `correlation_hints` 构建邻接表：
- concrete hints（confidence ≥ 0.6）→ 图边
- speculative hints（0.3 ≤ confidence < 0.6）→ 仅辅助提示
- confidence < 0.3 → 丢弃

这解决了"K8s pod 重启时间与 DB 慢查询时间窗口的关系未被发现"的经典问题。

**2. 因果链（Causal Chains）**

DFS 从入度为零的节点出发，仅保留路径上每个节点都有 ≥1 个 anomaly 的路径，按平均权重降序取前 5：

```text
Deployment(最新部署 < 2h) → K8s(Pod CrashLoopBackOff) → DB(慢查询激增)
```

这实现了从"知道多个数据源各有什么问题"到"理解问题之间的因果关系"的升级。

**3. 矛盾检测（Contradiction Detection）**

6 条硬编码规则，通过 SpecialistAnalysis 的 conclusion 前缀做确定性分类匹配（不依赖 LLM 比对）：
- K8s `异常:` + Metrics `正常:` → "可能非资源级故障"
- Log `异常:` + K8s `正常:` → "应用层故障，非基础设施"
- DB `异常:` + K8s `正常:` → "数据库层问题，非 K8s 层故障"

conclusion 前缀约定让矛盾检测仅通过字符串前缀做分类匹配，避免 LLM 二次调用的延迟和不确定性。

| 前缀 | 含义 | aggregate 行为 |
|------|------|---------------|
| `正常:` | 无异常 | 正常纳入 |
| `异常:` | 有异常 | 用于矛盾检测 |
| `部分:` | 产出不完整 | 权重 ×0.5 |
| `失败:` | 完全失败 | 不计入评分 |

**4. 矛盾检测扩展方向（后续版本）**

当前 6 条规则覆盖了常见 pairwise 矛盾。3+ Agent 的三角矛盾（如 K8s 异常 + DB 异常 + Metrics 正常 → "？"）尚未定义，后续可扩展为 N 元矛盾检测。

## 项目映射
- OpsPilot v1 诊断链路：证据链 → 根因假设 → 风险审查 → 处置方案
- OpsPilot v2 新增：aggregate 关联图 + 因果链 + 矛盾检测，从"做加法"升级为"做推理"
- 核心指标：根因假设置信度、证据覆盖率、诊断到处置的平均时间
- conclusion 前缀约定（正常:/异常:/部分:/失败:）让 aggregate 的交叉推理仅基于确定性字符串匹配

## 高频追问
1. 怎么保证根因假设是准确的？
2. 如果多个假设的置信度接近怎么办？
3. 诊断结果怎么和历史 RCA 关联？

## 我的回答要点
> 运维智能体的诊断不是让一个大模型直接拍板，而是两步走：Diagnosis Agent 基于证据链、历史 RCA 和 SOP 生成按概率排序的根因假设，Critic / Risk Agent 再反向检查证据是否充分、假设是否排他、操作风险等级。如果置信度不够或存在缺失证据，会建议补充采集。诊断结果带置信度和风险等级，高风险的操作必须人工审批后才能执行。
