## 运维智能体的核心表达

### 一句话定位
运维智能体不是替代运维人员，而是通过自动分诊、证据采集和根因假设加速故障定位，同时通过人工审批保证生产安全。

### 核心差异表达

| 对比维度 | 应用生成智能体 | 运维智能体 |
|---------|--------------|-----------|
| 目标 | 生成应用 | 诊断和处置故障 |
| 输入 | 自然语言需求 | 工单、告警、日志 |
| 核心链路 | Router → Planner → Codegen → QA | 分诊 → 证据 → 诊断 → 审批 → 执行 → RCA |
| 风险 | 生成错误代码 | 误操作生产 |
| 安全重点 | 权限、数据隔离、代码验证 | 人审、只读优先、模拟执行、回滚 |
| 产物 | 应用、代码、Schema | 根因、处置建议、RCA |
| 是否可以全自动 | 可自动（有 QA 验证） | 不可全自动（关键操作需人审） |

## 高频面试追问

### 1. 运维智能体和应用生成智能体的架构有什么不同？
> 应用生成智能体偏创造型任务，重点是生成正确应用；运维智能体偏诊断和决策任务，重点是证据链、安全边界和人审。两者都需要 Agent Workflow、Checkpoint 和日志审计，但风险控制重点不同。

### 2. 运维 Agent 为什么不能全自动执行？
> 运维场景涉及生产系统，错误动作可能造成事故。Agent 可以做证据收集、根因假设、处置建议，但重启、扩容、回滚、删除、配置变更这类写操作必须人工审批。我们的安全设计核心：只读优先 → 建议生成 → 人工审批 → 受控执行 → 验证 → RCA。

### 3. 证据采集怎么做？怎么保证证据可信？
> 先由 Evidence Planner 根据故障类型和严重程度判断要查哪些数据源，再并发发起采集。MySQL、K8s、ALB、OSS 各自通过只读接口采集，结构化后存入 Evidence Store。每条证据带置信度，原文放对象存储，数据库只存摘要和引用。

### 4. 怎么做到端到端闭环？
> 从工单接入到 RCA 复盘形成完整闭环：工单/告警 → 自动分诊 → 多源证据采集 → 根因假设 → 处置建议 → 人工审批 → 执行验证 → RCA 沉淀。RCA 沉淀到知识库后，未来故障可以复用历史诊断经验。

### 5. 审批卡点怎么设计？
> 高风险操作（重启、扩容、回滚、配置变更）必须人工审批。Remediation Agent 生成处置方案后进入 WAITING_APPROVAL 状态，审批通过后打 APPROVED checkpoint，然后先模拟执行再真实执行。审批可能隔很久，状态必须持久化到数据库，Worker 重启不丢状态。

### 6. 表设计有哪些设计思维？索引怎么设计？
> 运维表设计不是按 Agent 名字简单建表，而是按业务对象和执行过程来拆：工单（tickets）、故障（incidents）、服务（services）、证据（evidence_items）、诊断（diagnosis_results）、处置（remediation_plans）、审批（approvals）、执行（execution_records）、验证（verification_results）、RCA（rca_reports）。索引不是看到字段就加，而是围绕高频查询路径设计：service_id + 时间、incident_id + 时间、status + severity、approver_id + status。证据原文和大文件不塞数据库，引用存 OSS/S3。

### 7. Redis 和消息队列怎么设计？
> Redis 存短期运行态（任务状态、锁、SSE 事件缓冲、工具缓存、限流、心跳），不做最终事实源。消息队列负责异步任务解耦和失败重试：triage.queue、evidence.queue、diagnosis.queue、approval.queue、execution.queue、verification.queue、rca.queue。运维场景尤其适合消息队列，因为证据采集可以并发。

### 8. Checkpoint 怎么设计？
> 每个关键节点完成后落一个快照，包含 run_id、step_id、node_key、status、state_json、artifact_refs、input_hash、output_hash、idempotency_key、retry_count。运维场景需要在审批、执行、验证前后强制打 checkpoint，确保流程可恢复、可审计、可回放。

## 项目映射
- OpsPilot 全链路实现以上所有设计
- 可与应用生成平台的系统设计做对比回答，展示不同场景下的架构差异

## 我的回答要点
> 运维 Agent 面试回答的核心顺序：先讲为什么需要 Agent（传统运维人力排查慢），再讲核心链路（分诊 → 证据 → 诊断 → 审批 → 执行 → RCA），然后讲安全设计（为什么不能全自动、怎么控制风险），最后讲数据设计（表怎么拆、checkpoint 怎么打、Redis/MQ 怎么配合）。不要只说功能，要说出"安全边界"这个运维智能体最核心的设计约束。
