# 25.7 生产级Agent五性

> 所属分支：[[25-运维智能体-AIOps深水区✅/_index|25-运维智能体-AIOps深水区]]

## 一句话定义

判断一个运维 Agent 是否生产可用，不是只看它能不能回答问题，而是看它是否具备五个工程闭环：可评测、可观测、可复用、可扩展、可审计。

## 五维记忆口诀

> **评测看效果，观测看过程，复用看沉淀，扩展看规模，审计看责任。**

---

## 1. 可评测：证明效果有没有变好

### 解决的问题
这次改 Prompt、Planner、工具策略或 RAG 后，Agent 到底有没有提升？

### 运维 Agent 中的落地
- 通过历史/模拟故障构建离线评测集（10~20 个典型 Case）
- 每个 case 包含期望故障类型、期望证据源、期望根因和风险等级
- 工具返回用 fixture 固定，保证评测可复现
- 每次修改 Agent 后自动回放，输出指标

### 核心指标
| 指标 | 说明 |
|------|------|
| 根因 Top1/Top3 命中率 | 第一位/前三位候选根因是否命中 |
| 排查计划覆盖率 | 实际证据源 / 期望证据源 |
| 工具选择准确率 | 选对工具的比例 |
| 风险等级准确率 | P0-P3 分级正确率 |
| 人工接管率 | 需要人工干预的比例 |
| 平均排查耗时 | 从工单到根因确认的时间 |

### 三层评测体系
- **节点级**：单独评 triage/planner/tool_router，定位问题快
- **链路级**：评整条链路 end-to-end，更接近真实
- **在线级**：系统上线后看人工接管率、采纳率等业务指标

### 面试表达
> 可评测就是给 Agent 建一套考试系统：用固定工单、固定工具返回和标准答案，评估它有没有变好。

---

## 2. 可观测：看清每一步发生了什么

### 解决的问题
Agent 这次为什么这么判断？到底在哪一步出错？

### 运维 Agent 中的落地
六层观测：

| 层级 | 观测内容 |
|------|---------|
| Run 层 | 任务状态、总耗时、最终结论 |
| Node 层 | 每个工作流节点输入/输出/耗时 |
| LLM 层 | 模型、Prompt 版本、Token、耗时、解析状态 |
| Tool 层 | 工具名、参数、资源、结果、重试、错误 |
| Evidence 层 | 证据来源、支持/反驳哪个根因 |
| Human 层 | 审批人、审批结果、人工接管 |

### 技术实现要点
- 统一 Trace ID 体系：run_id / node_id / tool_call_id / llm_call_id / evidence_id
- 结构化 Event Log：node.started / tool.completed / llm.failed / evidence.created / approval.required
- 节点统一装饰器埋点
- SSE/WebSocket 实时推送到前端 RunDetail
- 脱敏与权限控制（不裸存完整敏感数据）

### 可观测 vs 可评测
- 可评测 = 考试分数（结果维度）
- 可观测 = 答题过程和草稿纸（过程维度）

### 面试表达
> 可观测就是给 Agent 装行车记录仪：每个节点、每次模型调用、每次工具调用、每条证据都能回放，从而知道它为什么这么判断、哪里失败、怎么优化。

---

## 3. 可复用：能力不要为单个故障写死

### 解决的问题
这套 Agent 能不能从"订单服务 500"复用到"支付超时""OSS 403""K8s Pod 异常"？

### 运维 Agent 中的落地
七层标准协议：

| 层级 | 标准对象 |
|------|---------|
| 工单层 | IncidentContext（统一故障上下文） |
| 计划层 | PlanStep（统一排查步骤） |
| 工具层 | ToolDefinition（统一工具定义） |
| 证据层 | EvidenceRecord（统一证据结构） |
| 风险层 | RiskPolicy（统一风险策略） |
| 审批层 | ApprovalCard（统一审批卡片） |
| RCA 层 | RCAArtifact（统一复盘产物） |

### 设计原则
- 新增故障类型 → 补充故障模板，不重写主流程
- 新增数据源（Redis/MQ/ES）→ 新增 Tool Adapter + Metadata，不动 Agent 主链路
- 新增业务服务 → 通过 CMDB 做资源映射
- 主流程固定：工单抽取 → 分诊 → 计划 → 工具采集 → 证据聚合 → 诊断 → 审批 → 验证 → RCA

### 面试表达
> 可复用就是把 Agent 从 case 编程升级为能力编程，靠标准协议、模板和 Adapter 扩展新场景。

---

## 4. 可扩展：规模上来后系统还能撑住

### 解决的问题
当工单变多、工具变多、团队变多、并发变高时，系统能不能稳定运行？

### 运维 Agent 中的落地
八层扩展：

| 层级 | 扩展方式 |
|------|---------|
| 任务执行 | Run + Queue + Worker 异步架构 |
| 工具接入 | Tool Registry 动态注册 |
| 工作流节点 | 状态机/图编排，支持新增/删除/跳过节点 |
| 状态存储 | Run/Checkpoint/Event/ToolCall/Evidence/Approval 全部持久化 |
| 并发与队列 | P0/P1/P2 优先级队列 + 工具/服务/租户限流 |
| 多租户/多团队 | tenant_id/team_id/service_id 权限隔离 |
| 数据源/云厂商 | 三层抽象：ToolDefinition → ToolAdapter → EvidenceNormalizer |
| 成本与性能 | 规则优先/模板优先/缓存优先/并行优先/压缩优先/小模型优先 |

### 架构表达
```text
Frontend → API Server（创建 Run）
  → Queue/Redis（任务排队、优先级、分布式锁、限流）
  → Agent Worker（执行 Workflow、保存 Checkpoint、发射 Events）
  → Tool Runtime（权限、参数、审批、重试、审计）
  → Tool Adapters（MySQL/K8s/ALB/OSS/Redis/MQ...）
  → Storage（runs/checkpoints/events/tool_calls/evidence/approvals/rca）
```

### 面试表达
> 可扩展就是让 Agent 从单机跑 Demo，升级成支持多工单、多工具、多团队、多并发的平台型系统。

---

## 5. 可审计：生产操作要能追责

### 解决的问题
Agent 查了什么？谁批准的？有没有越权？为什么执行这个动作？出了问题谁负责？

### 运维 Agent 中的落地
八类审计：

| 审计类别 | 记录内容 |
|---------|---------|
| 工单来源 | 工单 ID、来源、创建人、服务、环境、严重等级 |
| Agent 决策 | 为什么判断这是 P1？为什么排查 MySQL？为什么建议重启？ |
| 工具调用 | 谁调用、哪个 Agent、哪个资源、参数、结果摘要、耗时 |
| 权限判断 | 权限决策（ALLOW/DENY/REQUIRE_APPROVAL）、决策原因 |
| 审批记录 | 动作、资源、风险、证据、审批人、审批结果、审批时间 |
| 执行结果 | 执行成功/失败、耗时、重试次数、回滚方案 |
| 证据链 | 每个结论由哪些证据支持、哪些反证、置信度 |
| RCA 产物 | 完整复盘报告、确认人、归档时间 |

### 高风险动作强制规则
```text
没有 approval_id → 不允许执行
approval_id 状态不是 approved → 不允许执行
审批动作 ≠ 执行动作 → 不允许执行
审批资源 ≠ 执行资源 → 不允许执行
```

### 审计技术要点
- 审计事件表只 INSERT 不 UPDATE（append-only）
- 参数脱敏（Token/Cookie/手机号/AccessKey）
- 结果摘要化（不存完整原始结果）
- 原始数据引用存对象存储，按权限查看

### 可观测 vs 可审计
- 可观测：关心过程（为什么慢？哪里错？哪步失败？） — 给研发排障
- 可审计：关心责任（谁做的？有没有审批？能不能追责？） — 给安全合规

### 面试表达
> 可审计就是给 Agent 建一条责任链，从工单、决策、工具、审批、执行到 RCA，每一步都有记录、有证据、有责任人。

## 五性关系总览

| 维度 | 一句话 | 运维智能体中的关键落点 |
|------|--------|---------------------|
| 可评测 | 效果有没有变好 | 离线评测集、根因命中率、计划覆盖率 |
| 可观测 | 过程能不能看清 | Trace ID、Event Log、RunDetail 时间线 |
| 可复用 | 能力能不能迁移 | IncidentContext、ToolDefinition、EvidenceRecord |
| 可扩展 | 规模上来能不能跑 | Queue+Worker、Checkpoint、限流、动态工具注册 |
| 可审计 | 出事能不能追责 | 审批记录、工具审计、证据链、RCA |

## 项目映射

- OpsPilot 主链路已跑通，但五性中评测、RAG、Tracing、指标看板是当前最大短板
- ToolGateway 已有基础审计，但需升级为生产级审计（持久化+脱敏+审批绑定）
- 可复用的核心对象（IncidentContext、PlanStep、ToolDefinition、EvidenceRecord）已在架构中定义

## 高频追问

1. 五性里你觉得哪个最难落地？为什么？
2. 可观测和可审计到底有什么区别？为什么两者都需要？
3. 如果一个 Agent 五性都不具备，它算不算 Agent？

## 我的回答要点

> 我判断一个运维 Agent 是否生产可用，不会只看它能不能回答问题，而是看它有没有五个工程闭环。可评测解决效果问题——每次改 Prompt/Planner 后怎么判断有没有变好；可观测解决过程问题——每一步做了什么能不能看清和回放；可复用解决沉淀问题——能力不能为单个故障写死，要靠标准协议迁移；可扩展解决规模问题——工单和工具多了之后架构能不能撑住；可审计解决安全问题——生产操作必须可追溯、可追责。这五点合起来，才是我理解的生产级运维 Agent。
