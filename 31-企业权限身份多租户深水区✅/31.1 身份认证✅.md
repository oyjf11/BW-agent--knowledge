# 31.1 身份认证

> 所属分支：[[31-企业权限身份多租户深水区✅/_index|31-企业权限身份多租户深水区]]

## 子节点 / 待填充要点
- 企业 SSO / 一体权限接入
- tenant_id 来源与可信性
- 多租户用户与 active_tenant_id
- Supabase JWT 签发与传递

## 一句话定义
不重新造账号体系，通过接入企业已有 SSO / 一体权限系统获取可信 user_id 和 tenant_id，再签发 Supabase JWT 供前端携带访问业务数据。

## 解决什么问题
前端不可信：tenant_id 不能由前端自行传递，否则存在越权风险。需要一个从企业身份系统 → 平台后端 → Supabase JWT 的可信传递链。

## 如何实现

### 身份传递链路
```text
用户登录 → 企业 SSO / 一体权限系统
  ↓
平台后端获取可信 user_id / tenant_id
  ↓
后端签发 Supabase JWT（嵌入 user_id、tenant_id）
  ↓
前端 Supabase Client 携带 JWT 访问业务数据
  ↓
Supabase RLS 从 JWT 读取 tenant_id 做行级隔离
```

### tenant_id 可信性保证
- tenant_id 来自企业 SSO / 一体权限系统，不是前端自己传的
- 用户登录成功后，后端从可信身份系统拿到 user_id 和 tenant_id
- 后端放进 Supabase JWT 中签发
- 前端只能携带 token，不能随意修改 token 里的租户身份

### 多租户用户处理
- 企业权限系统返回用户可访问的租户列表
- 进入工作空间时确定 active_tenant_id
- JWT 放当前租户
- 切换租户时重新签发 token
- MySQL 存 app 与 tenant 的归属
- Supabase RLS 按 active tenant 隔离

## 项目映射
- 应用生成平台：企业 SSO 提供 user_id、tenant_id → 平台后端签发 Supabase JWT

## 高频追问
1. tenant_id 从哪里来？可信吗？
2. 如果一个用户属于多个租户怎么办？
3. 为什么不在前端过滤 tenant_id？

## 我的回答要点
> tenant_id 来自企业 SSO / 一体权限系统，不是前端自己传的。用户登录成功后，后端从可信身份系统拿到 user_id 和 tenant_id，再放进 Supabase JWT。前端只能携带 token，不能随意修改 token 里的租户身份。多租户用户不能简单把所有 tenant_id 都放开，更稳的方式是确定 active_tenant_id 后签发当前 Supabase JWT，切换租户时重新换 token。
