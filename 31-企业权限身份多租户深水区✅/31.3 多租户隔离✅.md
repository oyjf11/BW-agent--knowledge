# 31.3 多租户隔离

> 所属分支：[[31-企业权限身份多租户深水区✅/_index|31-企业权限身份多租户深水区]]

## 子节点 / 待填充要点
- Supabase RLS 策略（using / with check）
- JWT 中的 tenant_id 传递
- 前端过滤 vs 数据库层隔离
- 业务表 tenant_id 规范

## 一句话定义
通过 Supabase RLS 在数据库层基于 JWT 中的 tenant_id 实现行级租户隔离，不依赖前端过滤做安全边界。

## 解决什么问题
前端过滤只能提升体验，不能作为安全边界。用户可绕过前端直接请求接口或 Supabase。需要数据库层强约束保证租户隔离。

## 如何实现

### RLS 查询策略
```sql
create policy "tenant_isolation"
on customers
for select
using (
  tenant_id = auth.jwt() ->> 'tenant_id'
);
```

### RLS 写入策略
```sql
create policy "tenant_insert"
on customers
for insert
with check (
  tenant_id = auth.jwt() ->> 'tenant_id'
);
```

### 业务表 Schema 规范
```sql
create table customers (
  id uuid primary key default gen_random_uuid(),
  tenant_id text not null,
  name text not null,
  phone text,
  status text,
  created_by text,
  created_at timestamptz default now()
);
```

### 关键设计原则
- 每张业务表统一带 `tenant_id`，必要时带 `created_by` / `updated_by`
- 查询用 `using` 控制哪些行可见
- 写入用 `with check` 控制写入数据是否属于当前租户
- 建表模板强制注入 tenant_id
- 建表后强制启用 RLS

## 项目映射
- 应用生成平台：平台后端基于企业 SSO 拿到 tenant_id → 签发 Supabase JWT → 前端 Supabase Client 携带 → RLS 数据库层隔离

## 高频追问
1. 为什么不只在前端过滤 tenant_id？
2. RLS 的 `using` 和 `with check` 有什么区别？
3. tenant_id 从哪里来？如何保证可信？

## 我的回答要点
> 前端过滤只能提升体验，不能作为安全边界。用户可以绕过前端直接请求接口或 Supabase。RLS 是数据库层的强约束，即使用户绕过前端，只要 JWT 里的 tenant_id 和数据行的 tenant_id 不一致，数据库也不会返回数据。查询策略用 `using` 控制哪些行可见，写入策略用 `with check` 控制写入的数据是否属于当前租户。
