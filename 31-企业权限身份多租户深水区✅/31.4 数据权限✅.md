# 31.4 数据权限

> 所属分支：[[31-企业权限身份多租户深水区✅/_index|31-企业权限身份多租户深水区]]

## 子节点 / 待填充要点
- RLS using vs with check 区别
- 数据层隔离 vs 应用层过滤
- 动态建表时 RLS 自动注入
- 越权防护

## 一句话定义
在数据库层通过 Supabase RLS 实现数据权限，确保每个租户只能读写自己的数据，防止越权访问。

## 解决什么问题
只靠应用层过滤数据权限不可靠。需要数据库层的行级安全策略，使权限控制对任何访问路径（直接 API、前端、第三方调用）都生效。

## 如何实现

### RLS 策略对比
| 策略 | SQL 关键字 | 用途 | 示例场景 |
|------|-----------|------|----------|
| 查询隔离 | `using` | 控制哪些行可见 | 只返回当前租户的客户数据 |
| 写入校验 | `with check` | 控制写入数据归属 | 防止用户伪造 tenant_id 写入其他租户 |

### 数据权限层级
1. **数据库层（RLS）**：强约束，不可绕过
2. **应用中间件层**：租户上下文注入、请求校验
3. **前端体验层**：数据过滤、UI 隐藏（不可作为安全边界）

### 越权防护要点
- 前端不可信：tenant_id 不能由前端自行传递
- JWT 不可篡改：前端只能携带 token，不能修改 token 内容
- RLS 兜底：即使应用层校验被绕过，数据库也不返回越权数据
- 审计日志：所有数据访问记录操作人、租户、时间

### MySQL 与 Supabase 映射
```text
MySQL 存映射关系：
  app_id → tenant_id → supabase_project_id → table_name → rls_policy_version
```

## 项目映射
- 应用生成平台：所有动态建表自动注入 tenant_id 列 + 自动启用 RLS 策略
- MySQL 控制面存储 Schema 元信息和表映射，PG/Supabase 存储实际业务数据

## 高频追问
1. RLS 的 `using` 和 `with check` 有什么区别？
2. 为什么不只在前端过滤 tenant_id？
3. 如果一个用户属于多个租户怎么办？

## 我的回答要点
> 数据权限的核心是数据库层隔离，而不是前端过滤。查询用 `using` 限制可见行，写入用 `with check` 校验写入归属。前端过滤只能提升体验，RLS 是数据库层的强约束，即使用户绕过前端也无法越权访问数据。建表模板强制注入 tenant_id，建表后自动开启 RLS。
