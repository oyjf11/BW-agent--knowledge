# 33.2 流式体验

> 所属分支：[[33-AI原生交互体验深水区✅/_index|33-AI原生交互体验深水区]]

## 子节点 / 待填充要点
- 模型流式返回处理
- runnable 业务封装
- 流式态 vs 预览态分离
- Sandpack 卡顿优化
- 内网依赖问题

## 一句话定义
前端通过 runnable 业务对象消费 Together AI SDK 的流式输出，按内容类型（文本、代码、Schema、SQL）分发，流式态与预览态分离以避免 Sandpack 频繁编译卡顿。

## 解决什么问题
每个 token 触发 Sandpack 编译会导致页面卡顿；企业内网下 CDN 和外部依赖不可达导致预览失败。

## 如何实现

### runnable 业务封装
> runnable 不是 LangChain Runnable，是我们项目里对一次生成任务的封装。
```text
runnable
  ├─ input：用户需求、上下文、模型配置
  ├─ execute：调用 Together AI SDK
  ├─ stream：消费模型流式输出
  ├─ parse：拆分文本、代码、Schema、SQL
  ├─ dispatch：更新聊天区、代码区、预览区、状态区
  └─ final：返回最终代码和结构化产物
```

### 流式处理原则
- 前端不把所有流式内容直接塞进一个状态里
- 流式内容按类型分：文本说明、代码片段、Schema / SQL、状态信息
- 流式阶段轻量展示，避免频繁触发 Sandpack 和代码高亮重渲染
- 完整代码块结束后，再把最终代码提交给 Sandpack 预览

### 性能优化矩阵
| 问题 | 原因 | 解决 |
|------|------|------|
| 页面卡顿 | 每个 token 都 setState | buffer 批量刷新 |
| 代码高亮卡顿 | 长代码频繁重新高亮 | 延迟高亮 / 最终态高亮 |
| Sandpack 卡顿 | 每次代码变化都重新编译 | 流式态和预览态分离 |
| Preview 重建 | 组件卸载重挂载 | 隐藏代替卸载 |
| 内网依赖慢 | CDN / 外部依赖不可达 | 依赖白名单、本地化、shim |
| 大文件渲染慢 | React render 频繁 | useRef 缓存、虚拟化、分片更新 |

### Sandpack 企业内网坑
- 依赖下载受限：固定模板和依赖版本，做白名单
- CDN 不可用：本地化或 shim 常用库
- 版本不稳定：锁定依赖版本
- 编译/运行时错误统一收集 → 反馈给调试区和 QA Agent

## 项目映射
- Together AI SDK 流式返回 → runnable 消费 → parse 拆分 → dispatch 分发 → Sandpack

## 高频追问
1. 前端怎么处理模型流式返回？
2. 你们说的 runnable 是什么？
3. 流式代码生成为什么会卡？怎么优化？
4. Sandpack 在企业内网环境下有什么坑？

## 我的回答要点
> 我们把"流式生成态"和"可运行预览态"分开。模型生成时先轻量展示代码，不实时推给 Sandpack 编译。等代码块完整后，或者用户点击 Run，再提交给 Sandpack。这样可以避免每个 token 都触发打包和预览重建。runnable 是业务层对一次生成任务的封装，把 Together AI SDK 的模型调用、流式输出、任务状态和前端 UI 分发封装起来。
