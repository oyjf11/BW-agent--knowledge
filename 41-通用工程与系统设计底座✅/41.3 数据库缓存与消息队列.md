# 41.3 数据库缓存与消息队列

> 所属分支：[[41-通用工程与系统设计底座✅/_index|41-通用工程与系统设计底座]]

## 子节点 / 待填充要点
- Agent 系统的数据库设计总原则
- 通用运行表设计
- 应用开发智能体数据库
- 运维智能体数据库
- Redis 设计
- 消息队列设计

## 一句话总原则

> **数据库存长期事实和审计数据，Redis 存短期运行态和锁，消息队列负责异步任务解耦和失败重试。**

不要把所有东西都塞 Redis，也不要让消息队列承载业务状态。

## 一、数据库设计

### 通用运行表（两个智能体共用）

| 表 | 存什么 | 作用 |
|---|---|---|
| `agent_runs` | 一次完整任务运行 | 记录 run_id、用户、状态、入口参数 |

| `agent_checkpoints` | checkpoint 快照 | 失败恢复、断点续跑 |

| `agent_tool_calls` | 工具调用记录 | 调了什么工具、参数、结果、耗时 |
| `agent_approvals` | 人工审批 | 审批人、审批结果、审批意见 |

### 表设计思维

核心原则：**表不是按 Agent 名字建，而是按业务对象和执行过程拆。**

| 分类 | 包含的表 | 设计原因 |
|------|---------|---------|
| **事实表** | apps、services、incidents | 记录业务实体，变更少 |
| **过程表** | agent_runs、agent_steps、execution_records | 记录每次执行的过程状态，追加写不覆盖 |
| **产物表** | agent_artifacts、code_files、rca_reports | 记录中间和最终产物，大文件存 OSS/S3 引用 |
| **审计表** | agent_approvals、audit_logs、agent_errors | 记录审批和异常，用于追踪和恢复 |
| **优化表** | bad_cases、prompt_versions、historical_rcas | 沉淀知识用于未来优化 |
| **权限表** | tenants、tenant_members、approvals | 用于多租户隔离和人工审批 |

### 运维智能体特殊设计点

**为什么工单（tickets）和故障（incidents）要分开？**

- 一个工单可能对应零个或多个故障实例（用户报障但可能不是真实故障）
- 一个故障可能关联多个工单（多人同时报障同一个问题）
- 故障有独立生命周期（发现→诊断→修复→验证→关闭），工单有独立流转（客服→运维→关闭）
- 分开后可以独立索引、独立统计（工单量 vs 真实故障数），避免耦合

**为什么证据表和执行记录要追加写不覆盖？**

- 证据采集可能需要多次补充（第一轮证据不够，触发第二轮采集）
- 执行记录需要完整保留每次操作（模拟执行 + 真实执行 + 回滚执行）
- 追加写保证审计完整性，任何操作不可被篡改

### 索引设计思维

> 索引不是看到字段就加，而是围绕高频查询路径设计。

**应用开发智能体索引策略**

| 查询场景 | 索引设计 | 类型 |
|---------|---------|------|
| 查某个租户的所有应用 | `(tenant_id, created_at)` | 联合索引 |
| 查某个应用的所有版本 | `(app_id, version_no)` | 联合索引 |
| 查某个版本的所有文件 | `(version_id, file_path)` | 联合索引 |
| 查某个 run 的全部步骤 | `(run_id, step_order)` | 联合索引 |
| 查某个应用的当前版本 | `(app_id)` WHERE is_current = true | 部分索引 |
| 用户输入匹配 | `user_id, created_at` | 联合索引 |

**运维智能体索引策略**

| 查询场景 | 索引设计 | 类型 |
|---------|---------|------|
| 查某服务近期的故障 | `(service_id, created_at DESC)` | 联合索引 |
| 查某个故障的全部证据 | `(incident_id, created_at)` | 联合索引 |
| 筛选待处理的高优工单 | `(status, severity)` WHERE status = 'open' | 部分索引 |
| 查某人的待审批列表 | `(approver_id, status)` WHERE status = 'pending' | 部分索引 |
| 查某时间段的审计日志 | `(created_at, action_type)` | 联合索引 |
| 查相似历史 RCA | `service_id, root_cause_keywords`（GIN 倒排索引） | 全文索引 |

**索引设计原则**

1. **联合索引按查询频率排序**：最高频的查询条件放最前面
2. **部分索引减少空间**：如 `WHERE status = 'pending'` 只索引活跃审批
3. **唯一索引防重复**：如 `(run_id, node_key, idempotency_key)` 防止副作用重复执行
4. **大字段不建索引**：JSON 内容用倒排索引（GIN），大文本不索引用对象存储
5. **时间字段几乎都建索引**：Agent 运行数据查询几乎都带时间范围

## 二、Redis 设计

### 一句话原则

> **Redis 不做最终事实源，只做运行态加速。**

### Redis 存什么

| 类型 | Key 示例 | 作用 |
|------|---------|------|
| 任务运行状态 | `agent:run:{run_id}:status` | 前端快速查询 |
| SSE 事件缓冲 | `agent:run:{run_id}:events` | 流式展示过程 |
| 分布式锁 | `lock:run:{run_id}` | 防止同一个 run 被重复执行 |
| 幂等锁 | `idempotency:{step_id}` | 防止重复执行副作用节点 |
| 队列消费游标 | `stream:agent-events` | 事件推送 |
| LLM 临时上下文 | `ctx:{run_id}` | 避免频繁查 DB |
| 工具结果缓存 | `tool_cache:{hash}` | 避免重复查相同证据 |
| 限流计数 | `rate:user:{user_id}` | 控制模型调用频率 |
| 心跳 | `heartbeat:{worker_id}` | 判断 worker 是否存活 |

### 应用开发智能体 Redis 示例

```text
agent:run:run_001:status = "CODEGEN_RUNNING"
agent:run:run_001:current_step = "codegen_home_page"
agent:run:run_001:stream_events = [...]
lock:app:app_123 = "run_001"
sandpack:preview:run_001 = latest preview error
```

**作用**：
- 前端实时显示"正在生成页面 / 正在建表 / 正在预览"
- 防止同一个应用被两个生成任务同时修改
- 缓存 RAG 检索结果和当前项目快照

### 运维智能体 Redis 示例

```text
agent:run:run_789:status = "WAITING_APPROVAL"
lock:incident:inc_001 = "run_789"
tool_cache:k8s:order-service:pods = {...}
approval:run_789:ttl = 1800
heartbeat:worker:evidence-collector-01 = alive
```

**作用**：
- 工单处置过程中快速展示进度
- 防止同一个故障被多个执行器重复修复
- 缓存短期证据（30 秒内重复查询 K8s Pod 状态不必重复打到集群）

## 三、消息队列设计

### 一句话原则

> **消息队列负责异步解耦、削峰、重试、并发执行。**

### 技术选型

| 方案 | 适合场景 |
|------|---------|
| Redis Queue / BullMQ | 轻量 MVP，Node 生态友好 |
| Kafka | 大规模事件流、审计、回放、吞吐高 |
| RabbitMQ | 传统任务分发、可靠投递 |
| Redis Stream | 中等规模事件流 + 消费组 |

面试建议：
> MVP 阶段我会优先用 Redis Stream / BullMQ，复杂度低，和 Node Agent Runtime 结合方便；如果后续进入生产级大规模场景，再把事件流和任务队列迁移到 Kafka。

### 应用开发智能体队列

| Queue | 消费者 | 任务 |
|---|---|---|
| `router.queue` | Router Worker | 意图识别 |
| `planner.queue` | Planner Worker | 生成 UI / DB / Routing plan |
| `codegen.queue` | Codegen Worker | 生成代码 |
| `migration.queue` | Migration Worker | 执行 SQL |
| `qa.queue` | QA Worker | lint / tsc / preview |
| `deploy.queue` | Deploy Worker | 打包部署 |

消息体不要太大，只放引用：
```json
{
  "job_id": "job_001",
  "run_id": "run_123",
  "step_id": "step_codegen_home",
  "app_id": "app_456",
  "version_id": "ver_007",
  "payload_ref": "db://agent_steps/step_codegen_home/input"
}
```

### 运维智能体队列

| Queue | 消费者 | 任务 |
|---|---|---|
| `triage.queue` | Triage Worker | 工单分诊 |
| `evidence.queue` | Evidence Workers | 并发采集证据 |
| `diagnosis.queue` | Diagnosis Worker | 根因分析 |
| `approval.queue` | Approval Worker | 等待人工确认 |
| `execution.queue` | Executor Worker | 模拟 / 受控执行 |
| `verification.queue` | Verifier Worker | 验证恢复 |
| `rca.queue` | RCA Worker | 生成 RCA |

运维智能体尤其适合消息队列，因为证据采集可以并发：
```text
Evidence Planner
   ↓
发送 4 个 evidence jobs：
- 查 K8s Pod
- 查 MySQL 慢 SQL
- 查 ALB 5xx
- 查 OSS 访问错误
   ↓
所有 evidence jobs 完成
   ↓
Diagnosis Agent 开始分析
```

## 高频追问
1. 数据库为什么分控制面和数据面？
2. 证据原文怎么存？为什么不塞数据库？
3. Redis 和数据库之间怎么保证数据一致性？
4. 消息队列消费失败怎么处理？

## 我的回答要点
> 存储设计上，数据库是事实源，存 run、step、event、checkpoint、artifact、approval、tool_call、RCA 等结构化数据；Redis 存短期运行态、分布式锁、SSE 事件缓冲、工具结果缓存和限流，不做最终事实源；消息队列负责异步节点调度、并发证据采集、失败重试和削峰。表设计不是按 Agent 名字建，而是按业务对象和执行过程拆：事实表、过程表、产物表、审计表、优化表、权限表。索引围绕高频查询路径设计，时间字段几乎都建，联合索引按查询频率排序，大字段用对象存储引用不塞数据库。
