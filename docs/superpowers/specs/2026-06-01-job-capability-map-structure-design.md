# 双岗位能力地图结构补齐设计

## 1. 背景

当前知识库以“企业 AI 应用落地”为根节点，已经覆盖 Agent Runtime、RAG、Tool / MCP、EvalOps、安全治理、平台化和商业化等企业级 AI 主干能力。

本轮只补地图结构，不填充概念卡正文。目标岗位限定为：

1. 中国大陆高级 Agent 开发工程师。
2. 中国大陆 ToB 企业 AI / Agent 产品经理。

本轮不把 C 端 AI 产品增长、创作者生态、内容消费和全球化运营列为硬性能力。

## 2. 目标

在保留现有 `01` 至 `40` 分支编号和 Wiki 链接稳定性的前提下：

1. 建立两个目标岗位的原子能力清单。
2. 为每个原子能力指定一个主知识节点和零到多个辅助节点。
3. 追加缺失的通用工程、Agent 前沿、ToB 产品基本功和中国大陆 AI 合规分支。
4. 生成双岗位覆盖矩阵和结构覆盖审计报告。
5. 使两个岗位各自的加权结构覆盖率达到 `>= 95%`，且所有 `P0` 能力均有主知识节点。

## 3. 非目标

本轮不做以下工作：

1. 不填充概念卡中的定义、实现、项目映射、追问答案等正文。
2. 不重排、重命名或删除现有 `01` 至 `40` 分支。
3. 不扩展 `39.3` 至 `39.6` 的其他岗位模型。
4. 不修改用户当前正在编辑的 `05-Agent系统化落地层` 正文。
5. 不把“结构已覆盖”表述为“候选人已经掌握”或“面试已经准备完成”。

## 4. 设计原则

### 4.1 岗位模型作为入口

`39-岗位能力模型覆盖树` 是求职准备入口。知识树是被映射的知识底座。岗位模型不复制概念正文，只声明能力清单、优先级和知识节点链接。

### 4.2 只追加，不重排

新增一级分支使用 `41` 至 `44`。现有分支仅在职责明确时追加叶子节点，避免大面积链接变动。

### 4.3 主节点唯一

每个原子能力必须有且只能有一个主知识节点，可以有多个辅助节点。主节点用于覆盖率统计，辅助节点用于交叉学习。

### 4.4 结构状态与内容状态分离

本轮验收只判断能力是否存在可达的知识节点，不判断概念卡正文是否已经填充。新增概念卡沿用现有模板，保留 `status: todo` 和 `- 待补充`。

## 5. 方案选择

### 5.1 采用方案

采用“保留现有结构，追加缺失分支”的方案：

1. 新增 `41` 至 `44` 四个一级分支。
2. 扩展 `12`、`15` 和 `20` 三个既有分支。
3. 重写 `39.1`、`39.2` 两个岗位模型。
4. 新增 `39.7` 覆盖矩阵和 `99-附件` 下的审计报告。

### 5.2 未采用方案

不采用以下方案：

1. 把全部缺口塞入既有分支。原因：分支职责会混乱，长期难维护。
2. 按岗位重建整棵知识树。原因：重复内容过多，会破坏现有 Wiki 链接和当前编辑状态。

## 8. 岗位模型结构

重写以下文件：

1. `39-岗位能力模型覆盖树/39.1 高级Agent开发.md`
2. `39-岗位能力模型覆盖树/39.2 高级AI产品经理.md`

两个岗位模型使用相同章节：

```text
岗位定位
能力域
P0：面试高频，必须覆盖
P1：常见要求，应当覆盖
P2：加分项，按方向选修
能力清单与知识节点映射
项目证据映射
高频追问入口
当前覆盖统计
```

每项能力必须：

1. 使用稳定的能力 ID。
2. 标注优先级 `P0`、`P1` 或 `P2`。
3. 链接到唯一主知识节点。
4. 在适用时链接辅助知识节点。
5. 在适用时链接已有项目快捷入口。

能力 ID 规则：

```text
DEV-<能力域缩写>-<两位序号>
PM-<能力域缩写>-<两位序号>
```

示例：

```text
DEV-RUNTIME-01
PM-SCENE-01
```

## 9. 双岗位覆盖矩阵

新增：

`39-岗位能力模型覆盖树/39.7 双岗位能力覆盖矩阵.md`

矩阵是覆盖率计算的单一事实来源。字段固定为：

| 字段 | 含义 |
|---|---|
| 能力ID | 稳定且唯一的原子能力编号 |
| 岗位 | `高级Agent开发` 或 `ToB企业AI-Agent产品经理` |
| 能力域 | 能力所属分组 |
| 原子能力 | 可独立判断是否覆盖的能力描述 |
| 优先级 | `P0`、`P1` 或 `P2` |
| 权重 | `P0=3`、`P1=2`、`P2=1` |
| 主知识节点 | 唯一 Wiki 链接 |
| 辅助节点 | 零到多个 Wiki 链接 |
| 项目证据入口 | 已有项目快捷入口或 `无` |
| 结构状态 | `已映射` 或 `缺口` |

约束：

1. `能力ID` 全局唯一。
2. `主知识节点` 每行只能有一个。
3. `结构状态=已映射` 时，主知识节点文件必须存在。
4. `结构状态=缺口` 时，主知识节点必须填写计划新增的目标节点。
5. 同一能力不得为了提高覆盖率重复拆分成语义等价条目。

## 10. 覆盖审计报告

新增：

`99-附件/岗位能力覆盖审计-2026-05.md`

报告至少包含：

1. 评估范围与时间基线：截至 `2026-05-31` 的中国大陆岗位要求。
2. 两个岗位的能力域摘要。
3. 各岗位 `P0`、`P1`、`P2` 数量。
4. 各岗位总权重、已映射权重和加权结构覆盖率。
5. 所有未映射能力清单。
6. 所有新增一级分支和扩展节点清单。
7. 明确声明：结构覆盖率不等于知识掌握率或面试准备完成度。

## 11. 覆盖率算法

权重固定为：

```text
P0 = 3
P1 = 2
P2 = 1
```

岗位结构覆盖率：

```text
已映射能力权重之和 / 岗位全部能力权重之和
```

总体结构覆盖率只作为汇总信息，不替代岗位级验收：

```text
两个岗位已映射能力权重之和 / 两个岗位全部能力权重之和
```

## 14. 验收标准

### 14.1 硬性验收

1. 四个新增一级分支及其 `_index.md` 存在。
2. 所有声明的新叶子节点概念卡存在。
3. `39.1` 和 `39.2` 均包含岗位定位、分级能力、映射、项目证据、高频追问和覆盖统计。
4. 矩阵中不存在重复能力 ID。
5. 每条矩阵记录恰好包含一个主知识节点。
6. `结构状态=已映射` 的主知识节点文件均存在。
7. 两个岗位的加权结构覆盖率分别达到 `>= 95%`。
8. 两个岗位的所有 `P0` 能力均为 `已映射`。
9. 首页、完整知识树和附件知识地图均出现 `41` 至 `44` 分支。
10. 不修改禁止修改清单中的文件。

### 14.2 文档质量验收

1. 新增概念卡沿用现有概念笔记模板。
2. Wiki 链接可解析到存在的文件。
3. 岗位能力描述保持原子化，避免一行混入多个无法独立判断的能力。
4. 审计报告明确区分结构覆盖率和内容完成度。

## 15. 风险与控制

| 风险 | 控制方式 |
|---|---|
| 为追求 95% 人为拆碎能力项 | 矩阵中要求原子能力可独立判断，审计重复或语义等价条目 |
